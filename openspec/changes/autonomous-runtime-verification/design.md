## Context

FastFiles is a Windows-only, three-process native C++ system: `FastFilesIndexSvc` (privileged, `SeBackupPrivilege`-only Windows Service), `FastFilesEngine` (unprivileged per-session index owner), and `FastFiles` (Direct2D UI shell), joined by a hardened named-pipe IPC contract and a read-only shared-memory snapshot channel. Its correctness claims are almost all *runtime* claims — a pipe squatter is rejected, a non-genuine engine cannot pass handshake, the client group cannot control the service via SCM, degraded mode never hangs the UI, `SeBackupPrivilege` alone suffices for raw-volume access. None of these can be proven by compilation; they require building, installing, and exercising the real binaries on a real Windows host.

The current state is that this proof step is recorded as **"blocked in this environment"** on task after task (`establish-architecture-foundation` 1.4, 7.1–7.7, and the tail of every other change). Investigation for this change established that the stated cause — "no MSVC/CMake toolchain" — is false. This host has Visual Studio 2022 Community 17.14 (with `VC.Tools.x86.x64`, a bundled `cmake.exe` 3.31.6 and `ninja.exe`, and `VsDevCmd.bat`/`vcvarsall.bat`), Visual Studio Build Tools 2019 and 2026, and Windows 10 SDKs. The genuine gaps are narrower and specific: **(a)** nothing loads the Developer environment before invoking the compiler; **(b)** the current session is a standard (non-elevated) token, so service install / SCM / ACL / registry operations fail; **(c)** multi-session and custom-UI validation need infrastructure (a second logon, a UI-automation seam) that does not exist yet. This design builds the harness for (a) and (b) now, and defines the tier/skip contract that (c) plugs into later.

## Goals / Non-Goals

**Goals:**
- Let the agent autonomously go Build → Install → Run → Verify → Diagnose → Repair → Re-run → Report, and only then archive an OpenSpec change.
- Deliver real, immediate value on *this* machine: Tier 0 (build + static + `ctest`) with zero new installs; Tier 1 (elevated single-session runtime) via on-demand elevation.
- Make honesty structural: a check whose required execution context is absent reports `SKIPPED(reason)`, and the archive gate distinguishes PASS from "SKIPPED but required."
- Keep the OpenSpec spec-driven discipline intact through the repair loop — auto-repair the harness freely, but never let auto-edited product code slip past the gate unrepresented in tasks/specs.
- Leave the host clean: mandatory idempotent teardown (uninstall, restore state) after every Tier-1 run, and support fully disposable environments so validation need not touch a developer machine at all.
- Be **modular and extensible**: validation areas are independently discoverable capabilities behind one versioned interface, so new capabilities are added without modifying the orchestrator core.

**Non-Goals:**
- Tier 2 (multi-session, Session 0, Fast User Switching, RDP) and Direct2D UI automation — deferred to a follow-up change; this change only defines their SKIP contract.
- Tier 3 (stress, soak, long-running leak/pressure) — deferred to a follow-up change.
- A general-purpose CI system, a cloud runner fleet, or cross-platform support (FastFiles is Windows-only by construction).
- Replacing human review of product-code changes; the harness proposes and gates, it does not silently commit fixes to product source.

## Decisions

### D1: Execution-context **tier model**, and this change delivers Tiers 0–1
Every validation declares the execution context it needs. Tiers, by ascending requirement: **0** build + static + user-mode tests (no elevation, no infra); **1** elevated single-session runtime (one admin token); **2** multi-session + UI (2nd logon + UI-automation seam); **3** stress/soak (time, scale, disposable host). Rationale: the 16-section brief has no natural single ordering, but it has a clean partial order by *what execution context each check demands* — which is exactly what was actually missing. Delivering 0–1 unblocks the entire currently-stalled foundation set; 2–3 are the genuinely infra-heavy tail and would otherwise gate everything behind the hardest, least-deterministic work. *Alternative considered:* order by product subsystem (build, service, IPC, UI…) — rejected because it interleaves trivially-runnable checks with infra-blocked ones inside every group.

### D2: Orchestrator in **PowerShell**, capabilities as plugin modules, native probes in a small `fftest.exe`
The control **core** (registry, scheduler, tier gating, run tree, gate, reporting, repair driver) is PowerShell 7 modules under `verify/`; each **capability** is a separate module implementing the shared interface (D11) and is discovered by the core, not hard-wired into it. Rationale: PowerShell is already present, needs no build (the thing that validates the build must not itself require the build), can elevate, and has first-class cmdlets for SCM (`Get-Service`/`sc.exe`), ACLs (`Get-Acl`), registry, Event Log (`Get-WinEvent`), ETW (`logman`/`wpr`), scheduled tasks, and `Get-AuthenticodeSignature`. A native `fftest.exe` (a CMake target linking the product libs) exists **only** for probes that must run *inside* a service/SYSTEM token or exercise product internals directly (e.g. `SeBackupPrivilege` sufficiency, pipe-ACL/handshake probes, shared-memory mapping). *Alternative considered:* a single C++ harness — rejected on the bootstrap paradox and the weaker Windows-admin ergonomics.

### D3: Build via `vswhere` → `vcvars` → **VS-bundled CMake + Ninja**, no global installs
Toolchain discovery uses `vswhere -latest -requires Microsoft.VisualStudio.Component.VC.Tools.x86.x64`; the Developer environment is activated by importing `VsDevCmd.bat`/`vcvarsall.bat` into the harness process env; configure/build use the CMake and Ninja bundled under the VS installation. Debug and Release are CMake presets; static analysis is a preset adding `/analyze` (the tree already builds `/W4 /WX`). Rationale: reproducible, self-contained, and it works on this host as-verified. The selected toolset (2019/2022/2026) is recorded in the run fingerprint so `/WX` breakage from a newer toolset is attributable and the toolset is selectable. *Alternative considered:* requiring a user-installed system CMake on PATH — rejected; unnecessary and less reproducible.

### D4: **JSON contracts + a per-run artifact tree** as the single source of truth
Each run is a directory `verify/runs/<change>/<timestamp>/` containing `manifest.json` (environment fingerprint), `index.json` (the core-built metadata index over all capability artifacts, per D16), a namespaced `artifacts/<capability>/…` subtree written by each capability (its `result.json` envelope plus capability-specific payloads — e.g. `artifacts/diagnostics/etl/…`, `artifacts/filesystem/scan.json`), `repair-log.jsonl`, and `report.{md,html,json,xml}`. Suites/capabilities are declared by **descriptors** (id → command → tier → required privileges → pass/fail predicate → on-failure diagnostics). Rationale: the agent, the reporter, and the gate all read the same typed artifacts instead of scraping console output; adding a validation is adding a descriptor entry (extensibility surface). Reports (md/html/json/junit) are pure projections of these artifacts.

### D5: **Environment fingerprint + four-state outcome**, never a silent pass
Before running, the harness records OS build, toolset+SDK versions, elevation state, session id/kind, and target identity. Each capability first exposes an **availability probe** (D11) evaluated against the fingerprint and its own external-tool prerequisites; the run outcome is one of four states: `PASS`, `FAIL`, `SKIPPED` (ran-nothing, context/prereq absent, with machine-readable `reason` + `requiredContext`), and — at the gate level — `REQUIRED-BUT-UNAVAILABLE` (a capability the change *requires* was `SKIPPED`). Rationale: the failure mode that destroys trust in autonomous validation is a check that "passes" because it never actually ran; separating "unavailable" from "passed" *and* from "required-but-unavailable" lets the gate (D8) refuse to archive when something mandatory could not run, while still archiving changes that legitimately do not touch that capability. *Alternative considered:* three states (pass/fail/skip) — rejected because it cannot express "this SKIP is disqualifying for *this* change."

### D6: **Environment Providers** — this host by default, disposable environments as first-class targets
The execution target is an **Environment Provider** behind one interface (`provision → activate → collect-logs → cleanup → snapshot-restore-if-supported`). Providers: `local` (this host; Tier 0 in the current session, Tier 1 via an admin token obtained on demand — elevated shell or a one-time human-approved elevated scheduled task — with **mandatory idempotent teardown** even on failure), `hyper-v`, `vmware`, `virtualbox`, `windows-sandbox`, `github-actions` (hosted Windows runners), and `self-hosted-runner`. Snapshot-capable providers restore to a clean baseline per run; ephemeral providers (Windows Sandbox, hosted runners) are inherently disposable; the `local` provider relies on teardown to leave the developer machine clean. Rationale: the fastest path to first results is `local`, but binding validation to one developer box pollutes it over time and cannot give Tier 2 multi-session isolation — the provider abstraction gives both without rewriting any capability, since capabilities target the provider interface, not a host. *Alternative considered:* require a VM up front — rejected as slower to first result; kept as a first-class, recommended provider for isolation-sensitive and Tier-2/3 work.

### D7: **Repair-loop fix classification**, no-progress detector, hard retry cap
The loop classifies every proposed fix. **Class A** (harness/config/environment: a wrong pipe name in a descriptor, a missing preset, an unset SDK path) is auto-applied and logged. **Class B** (product source) is applied on a work branch with a recorded root-cause and diff, but is **gated**: it must map to a task/spec, and it is surfaced for review — never silently archived. A **failure-signature** hash (normalized error + failing capability + phase) detects no-progress: the same signature twice ⇒ stop and escalate. When a failure is a crash, the loop's root-cause step consumes the **Crash Analysis** capability's output (D13) — classification bucket + resolved top frames — as structured input rather than re-deriving it. A hard iteration cap bounds total loops. Rationale: an unconstrained loop "fixes the test," masks real defects, and diverges from the spec; the classification keeps autonomy where it is safe and inserts a gate where it is not. Every iteration appends to `repair-log.jsonl`.

### D8: **Four-state archive gate** with two hard invariants
The gate consulted by the OpenSpec archive flow resolves each required capability to one of `PASS` / `FAIL` / `SKIPPED` / `REQUIRED-BUT-UNAVAILABLE`, and passes only when: (1) every capability the change's **gate policy** marks required is `PASS` (a required capability that is `FAIL` or `REQUIRED-BUT-UNAVAILABLE` blocks the gate; only capabilities the policy marks non-required may be `SKIPPED`); **and** (2) the run contains **no product-source edit that is not represented** in the change's tasks/specs. Rationale: (1) prevents archiving both on failures *and* on mandatory checks that never ran (the `REQUIRED-BUT-UNAVAILABLE` state — e.g. a change that touches the UI must not archive while UI Automation was SKIPPED for lack of a UIA context); (2) preserves spec-driven traceability against D7's Class-B edits. The gate reads only D4 artifacts plus the per-change gate policy, so its verdict is reproducible.

### D9: **Reuse existing self-verification** wherever it already exists
The product already ships much of its own verification: `ffindexsvc::VerifyBackupPrivilegeSufficiency` (privilege self-check), `ffindexsvc::VerifyClientAtHandshake` (impostor rejection), `ffsetup::BuildServiceObjectSecurityDescriptor` (SCM lockdown), and `tests/protocol/test_fuzz.cpp` (seeded frame/parse fuzzing wired into `ctest`). Rationale: a large fraction of this capability is orchestration + evidence capture + gating, not new test logic. `fftest.exe` wraps these as invokable probes; the harness runs them and captures their JSON/exit codes. New probe code is written only where no in-product check exists.

### D10: **Diagnostics + reporting** are collected on failure and projected, not narrated
Diagnostics is itself a registered capability that orchestrates Windows-native tooling, each availability-probed (absent tool ⇒ that collector `SKIPPED`, never a harness failure): Event Viewer channels (`Get-WinEvent`); ETW / **Windows Performance Recorder** traces (`wpr`/`logman`) with **WPA**-openable `.etl` output; **Process Monitor** (ProcMon) boot/runtime capture; **ProcDump** for on-exception/hang dumps; **Application Verifier** + **PageHeap** enabled for reliability/leak runs to surface heap and handle misuse early; **WinDbg/`cdb`** for post-mortem stack resolution (feeding D13); WER/mini dumps to a run-local, admin-only path; installer/MSI logs; and IPC traces. Reports are generated as Markdown (human summary), HTML (self-contained, shareable), JSON (machine), and JUnit XML (CI/tooling), plus a performance summary (vs. baseline, D14) and a failure summary with linked crash-analysis artifacts. Rationale: separates *evidence capture* from *presentation*; every report format is a deterministic projection of the same run tree, and native tooling gives enough context for rapid root-cause without manual reproduction.

### D11: **Capability registry** and versioned plugin interface
Every capability implements a common contract: `id`, `interfaceVersion` (semver), `tier`, `availability()` (probe → available | `SKIPPED(reason, requiredContext)`), `run(context) → result.json`, `diagnostics()` (declared collectors), and optional `baseline()`/`repair-hints()`. The core discovers capabilities by scanning the capability module directory, validates each against the interface schema and a supported `interfaceVersion` range, and refuses to load a capability declaring an incompatible version (recorded as a load diagnostic, not a silent drop). Adding a capability = dropping in a conforming module; the core is untouched. Rationale: modularity and long-term extensibility without editing the orchestrator; explicit interface versioning lets the core and capabilities evolve independently and makes breakage detectable. *Alternative considered:* a fixed switch over known suite ids — rejected as the monolith this refactor removes.

### D12: **UI Automation via UIA**, not pixel comparison; Tier 2
The UI Automation capability drives `FastFiles` through the Windows UI Automation provider tree (control identity, patterns, properties, and raised events), asserting on element structure/state and dispatching keyboard/mouse input through UIA and `SendInput`. It verifies launch, directory navigation, multi-column interaction, selection, keyboard navigation, connection-badge state, dialogs, scrolling, search, and error states; "rendering where practical" is asserted via UIA-exposed geometry/state and, only where UIA cannot express a property, a *tolerant, structure-scoped* visual check — never whole-screen pixel diffing. Because FastFiles renders its columns with Direct2D/DirectComposition rather than standard controls, a prerequisite is that the UI expose a **UIA provider** for its custom surface; where that provider is incomplete, affected checks `SKIP` with a precise reason rather than fall back to brittle pixels. Rationale: UIA is the Windows-native, resolution/theme-independent contract and avoids the flakiness that sinks pixel-based UI testing. *Alternatives considered:* pixel/image diffing (rejected — brittle, DPI/theme-fragile); input-replay macros (rejected — no state assertions).

### D13: **Crash Analysis** as a dedicated capability, wired into the repair loop
On any monitored-process crash (detected via ProcDump/WER or a non-zero fault exit), Crash Analysis: captures the full/mini dump to the run tree, resolves symbols (local PDBs from the build, optionally a symbol server), generates a stack trace, **classifies** the crash (bucket by faulting module + exception code + top normalized frames), preserves reproduction artifacts (inputs, environment fingerprint, the failing capability's context), and attaches everything to the report. Its structured verdict is the input to the repair loop's root-cause step (D7). Rationale: crashes are the highest-value, highest-effort failures to diagnose; making them a first-class capability with a stable output contract lets the repair loop act on them and lets reports carry a real root cause, not just "it crashed."

### D14: **Historical performance baselines** with configurable thresholds
Performance is stored, not just measured: each metric (startup, indexing throughput, IPC latency, memory, CPU, handle count) is written to a per-fingerprint **baseline store** (`verify/baselines/<fingerprint>/…`) keyed by environment fingerprint so runs are only compared like-for-like. A run compares against the rolling baseline (e.g. median of the last N same-fingerprint runs) and flags regressions using **configurable thresholds** (absolute and/or percentage, per metric). First run for a fingerprint seeds the baseline instead of reporting a spurious regression. Threshold breaches are advisory by default and become gate-affecting only when the change's gate policy opts in. Rationale: one-off numbers can't catch drift; per-fingerprint history + tunable thresholds separate real regressions from hardware noise. *Alternative considered:* a single global baseline — rejected because cross-machine/toolset variance would swamp real signal.

### D15: **Dedicated filesystem validation** for core product behaviors
FastFiles' value is its index over the filesystem, so filesystem edge cases are product behaviors, not incidental I/O: the Filesystem capability gets explicit checks for very large directory trees, NTFS permissions, symbolic links, junctions, generic reparse points, alternate data streams, long (`\\?\`) paths, deleted files, renamed/moved directories, locked files, incremental indexing, **USN journal recovery** (journal wrap/reset/ID change), and **stale-index recovery**. Rationale: these are exactly where an indexer silently goes wrong; giving each a named check with captured evidence is what makes "the index is correct" a testable claim.

### D16: **Capability Artifact Contract** — the core archives and indexes, never parses capability internals
Every capability writes its outputs into its own namespaced subtree `artifacts/<capability>/…` and emits, at that subtree's root, a common `result.json` **envelope** (id, interface version, tier, outcome, timing, and a list of produced artifact paths + types) — the only file the core reads. Everything else under the subtree (e.g. `artifacts/diagnostics/etl/*.etl`, `artifacts/diagnostics/procmon/*.pml`, `artifacts/diagnostics/dumps/*.dmp`, `artifacts/filesystem/scan.json` + `repair.json`, `artifacts/performance/benchmark.json`, `artifacts/ui/automation.json`) is **opaque to the core**. The core's job is exactly two things: (1) archive the whole `artifacts/` tree, and (2) build `index.json` from each envelope's declared metadata. The core SHALL NOT parse capability-specific payloads, and reporters/gate consume envelopes + `index.json`, drilling into payloads only via the paths the envelope declares. Rationale: this is what keeps the registry (D11) actually decoupled — a new capability can emit any internal format it likes without the core knowing anything about it, and the core never grows capability-specific branches. It also makes runs self-describing and portable: the index + envelopes are enough to render a report or evaluate the gate without re-running anything. *Alternative considered:* a single shared result schema every capability must flatten into — rejected because it forces capability internals into the core's vocabulary and re-couples exactly what the registry decouples; the envelope carries only the *common* fields, and payloads stay capability-owned.

## Risks / Trade-offs

- **Autonomous admin agent on a real machine (blast radius)** → Bounded by an allowlisted destructive-verb set, scoped/temporary elevation (not a blanket-admin agent), mandatory idempotent teardown, a hard rule that the harness never disables product hardening to make a check pass, and the option to retarget a disposable VM. Every state-mutating op captures pre/post state.
- **Repair loop masking real bugs ("fixing the test")** → D7 fix classification + D8 gate invariant (2): product-code edits are gated, root-cause-logged, and traceable; no-progress detector + retry cap stop thrash.
- **Silent false confidence from unrun checks** → D5 SKIP-with-reason + D8 gate treating "SKIPPED but required" as not-passing.
- **Toolset drift across 2019/2022/2026 breaking `/WX`** → toolset recorded in the fingerprint and selectable per run; a warning that a new toolset's diagnostics differ is a Class-A finding, not a silent failure.
- **Runtime timing flakiness (service start, pipe connect)** → suites use bounded polling with explicit timeouts and idempotent teardown; a suite may declare a small retry budget; fingerprint + seeds make reruns comparable.
- **UAC/elevation friction interrupting autonomy** → one-time human-approved elevated harness host (elevated shell or scheduled task) instead of a prompt per operation; documented in the migration plan.
- **Performance baselines drifting on shared hardware** → baselines are host-scoped and stored per fingerprint; comparisons flag regressions as advisory unless a threshold policy is set, so noisy hardware does not red-gate a change.
- **Over-broad scope stalling the change** → Tier-2/3 *execution environments* explicitly deferred; UI Automation and Stress are registered and specified but SKIP until their infra exists, so archival depends only on Tier-0/1. This change ends at "foundation 7.1–7.7 close through the harness."
- **Capability plugin model adds indirection/complexity** → One small interface (D11) with a schema-validated contract and version check; the core stays a registry+scheduler+gate. The alternative (a growing monolith) is the very cost this refactor removes. Complexity is bounded by keeping cross-cutting concerns (diagnostics, crash, env, gate) in the core, not duplicated per capability.
- **UIA flakiness / missing provider on the Direct2D surface** → Assert on the UIA tree and events (not timings or pixels); where the custom surface lacks a UIA provider, `SKIP` with a precise reason instead of falling back to brittle checks — making the provider gap visible as work, not as a flaky pass/fail.
- **Native diagnostic tools absent (WinDbg/WPR/ProcMon/AppVerifier)** → Each collector is availability-probed; absence yields a `SKIPPED` collector and a note in the report, never a harness failure. Crash Analysis degrades to dump-only capture when symbols/WinDbg are unavailable.
- **Disposable-environment provisioning cost/fragility** → Providers are opt-in behind one interface; `local` remains the zero-provisioning default. Snapshot restore and hosted runners trade setup cost for isolation and are recommended for isolation-sensitive/Tier-2/3 work, not forced on every run.
- **Baseline noise on shared hardware causing false regressions** → Baselines are per-fingerprint with rolling medians and configurable thresholds; advisory by default, gate-affecting only on explicit policy opt-in.

## Migration Plan

1. Land Tier 0 first (harness core + build validation) — provable immediately on this host with no elevation; wire the existing `ctest` suites in.
2. Add `fftest.exe` probes and Tier 1 suites (install/service/privilege/IPC/filesystem/reliability/perf); validate against an elevated context with mandatory teardown.
3. Establish the elevated execution context: document the one-time approved elevated harness host (elevated shell or scheduled task); confirm teardown leaves the host clean across repeated runs.
4. Integrate the archive gate into the OpenSpec archive flow (advisory first, then blocking).
5. **Prove the capability** by running the harness against `establish-architecture-foundation` and closing tasks 1.4 and 7.1–7.7 with real PASS evidence in a run tree; produce the first full report.
6. Rollback: the harness is additive tooling under `verify/` plus CMake presets/targets; disabling the gate step and removing `verify/` reverts with no product-source impact.

## Open Questions

- **Long-term elevated context**: standing SYSTEM/admin scheduled task that the agent triggers, vs. always launching from an elevated shell? (Leaning: approved scheduled task for unattended runs, elevated shell for interactive.)
- **Performance regression policy**: advisory-only vs. threshold gating, and where baselines live across machines/fingerprints.
- **Class-B human ack**: should a gated product-code fix require explicit human acknowledgment even when it maps cleanly to an existing task, or is task/spec representation sufficient for the gate?
- **Gate strictness for SKIPPED**: which SKIP reasons are acceptable per change, i.e. how is each change's gate policy authored — hand-written per change, or inferred from which product areas the change's tasks/specs touch (e.g. a change touching only the protocol library auto-requires IPC but not UI Automation)?
- **VM/provider default trigger**: at what point (Tier 2 work, or a security-sensitive change) do we switch the default Environment Provider from `local` to a snapshot-restorable VM or hosted runner?
- **Capability interface version policy**: what is the supported `interfaceVersion` compatibility window between the core and capability modules, and how are breaking interface changes rolled out?
- **UIA provider ownership**: does the Direct2D/DirectComposition UI need to ship a custom UIA provider (a product-code change tracked elsewhere) for UI Automation to reach full coverage, and what is the interim SKIP surface until then?
- **Baseline store location & retention**: where does `verify/baselines/` live (in-repo vs. external store), how many runs form the rolling window, and what is the retention/pruning policy?
- **Symbol strategy for Crash Analysis**: local PDBs only, or a configured symbol server; and how are stripped/release builds symbolized?
