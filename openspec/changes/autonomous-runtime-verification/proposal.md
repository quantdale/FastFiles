## Why

Every FastFiles change eventually hits the same wall: the last tasks — the ones that prove the privileged service, the named-pipe security model, the degraded-mode fallback, and the installer actually work — are marked **"blocked in this environment: no Windows/MSVC toolchain to build and run."** In `establish-architecture-foundation` alone, tasks 1.4 and 7.1–7.7 are all stalled on this; the same wall sits in front of every downstream change. The blocker was diagnosed as "no toolchain," but that is not true: this host already carries Visual Studio 2022 (with a bundled CMake 3.31 + Ninja and the full VC toolset), Build Tools 2019 and 2026, and the Windows 10 SDKs. The real gap is that **the agent has no harness that loads the Developer environment, builds, installs, runs runtime validation on a real Windows machine, diagnoses failures, repairs, re-runs, and gates the OpenSpec archive on the result.** This change builds that harness so runtime verification becomes a normal, autonomous step in the implementation lifecycle instead of a permanent "blocked" note.

## What Changes

- Introduce an **autonomous runtime-verification harness** the agent drives through a small set of verbs (`build`, `install`, `run <capability>`, `diagnose`, `report`, `repair`, `gate`), each emitting structured JSON into a per-run artifact tree.
- Structure the harness as a **capability registry** rather than a monolith: each validation area (Build, Installer, Windows Service, Privilege, IPC, Filesystem, UI Automation, Diagnostics, Performance, Stress, Crash Analysis, Repair Loop, Archive Gate) is an **independently discoverable capability** implementing a common versioned interface. The agent probes the registry at runtime, executes only the capabilities whose prerequisites are met, and a capability whose context is absent returns `SKIPPED(reason)` — never a spurious PASS or FAIL.
- Make the **archive gate four-state**: it distinguishes `PASS`, `FAIL`, `SKIPPED`, and `REQUIRED-BUT-UNAVAILABLE`, so a change can never be archived while a capability the change *requires* is merely unavailable.
- Add **UI Automation** as a first-class capability driven by Windows UI Automation (UIA), not brittle pixel comparison — launch, directory navigation, multi-column interaction, keyboard and mouse input, connection-badge/dialog/scroll/search/error-state verification, and rendering checks where practical. It is registered now and executes when an interactive UIA context is available, otherwise `SKIPPED`.
- Add a dedicated **Crash Analysis** capability (dump capture, symbol resolution, stack traces, crash classification, reproduction-artifact preservation) that feeds the repair loop's root-cause step and attaches its findings to the report.
- Expand **Diagnostics** to orchestrate Windows-native tooling where appropriate — ETW, Windows Performance Recorder/Analyzer (WPR/WPA), Process Monitor, WinDbg, Application Verifier, PageHeap, and ProcDump — collected automatically on failure with enough context for rapid root-cause analysis.
- Add an **Environment Provider** model so the harness can run against disposable/isolated Windows environments (Hyper-V, VMware, VirtualBox, Windows Sandbox, GitHub Actions Windows runners, self-hosted runners) with lifecycle management (provision → validate → collect logs → cleanup → snapshot restore), reducing long-term pollution of developer machines.
- Upgrade **Performance** from one-off measurement to a **historical baseline store** (startup, indexing, IPC latency, memory, CPU, handle counts, throughput) with regression detection against configurable thresholds.
- Organize all capabilities into an **execution-context tier model** so each declares the context it needs and reports `SKIPPED(reason)` — never a silent PASS — when that context is absent:
  - **Tier 0 (build + static + user-mode tests)** — configure MSVC via `vswhere`→`vcvars`, CMake configure, Debug/Release/clean/incremental builds, `/analyze` static analysis, compiler-diagnostics parsing, and the existing `ctest` unit + fuzz suites. Runs on this host today with no elevation and no new installs.
  - **Tier 1 (elevated single-session runtime)** — install/upgrade/repair/uninstall; SCM service lifecycle; privilege/token/integrity/ACL checks; engine↔service handshake, Authenticode pinning, heartbeats, reconnection; named-pipe & shared-memory IPC end-to-end incl. malformed/large payloads; filesystem validation; single-session reliability (crash/recovery/leak); diagnostics collection; performance baselines. Needs one elevated context, obtained on demand.
- Deliver a bounded **autonomous repair loop** (Implement→Build→Install→Run→Verify→Diagnose→Root-cause→Fix→Rebuild→Reinstall→Re-run) with a **fix classification** that auto-applies harness/config fixes but gates product-code fixes, a no-progress detector, and a hard retry cap — every iteration logged, and consuming Crash Analysis output at the root-cause step.
- Deliver **reporting** in Markdown, HTML, JSON, and JUnit XML, plus a performance summary and failure summary, backed by collected diagnostics (Event Log, ETW/WPR traces, WER/mini dumps + resolved stacks, installer logs, IPC traces) and linked crash-analysis artifacts.
- **Integrate into the OpenSpec workflow**: a four-state archive gate (`PASS`/`FAIL`/`SKIPPED`/`REQUIRED-BUT-UNAVAILABLE`) that blocks archival until every capability the change requires is `PASS` (or acceptably `SKIPPED`), never passing while a required capability is unavailable, and refusing to pass on a run whose product-code edits are not represented in the change's tasks/specs.
- **Unblock the foundation**: re-run and close `establish-architecture-foundation` tasks 1.4 and 7.1–7.7 through the harness as the capability's first real proof.
- **Registered now, execution tier-gated** (not fully deferred): **UI Automation** and **Stress** are defined as first-class registered capabilities with full interface specs in this change, but their execution requires **Tier 2** (interactive/multi-session UIA context) and **Tier 3** (time/scale/disposable host) respectively, and they report `SKIPPED(context-absent)` until that infrastructure exists — so this change still archives on Tier 0/1 results.
- **Explicitly out of scope for this change** (execution deferred to follow-up changes that add the infrastructure, not the interfaces): standing up a real **Tier 2** multi-session/Session-0/FUS/RDP + interactive-UIA execution environment, and a real **Tier 3** stress/soak/long-running leak/pressure execution environment. This change registers those capabilities and specs their contracts; the follow-ups provide the environments that let them run instead of SKIP.

## Capabilities

Each spec file below corresponds to one or more registered capabilities; the harness core spec defines the registry, the interface/versioning contract, and the cross-cutting capabilities (Diagnostics, Crash Analysis, Environment Providers, Repair Loop, Archive Gate).

### New Capabilities
- `runtime-verification-harness`: The orchestrator core — the **capability registry** and its versioned plugin interface, runtime capability discovery/availability probing, execution-context fingerprinting, the tier model and four-state SKIP/unavailable contract, the per-run artifact tree and JSON result contracts, **Diagnostics** (incl. native tooling: ETW/WPR/WPA/ProcMon/WinDbg/AppVerifier/PageHeap/ProcDump), **Crash Analysis**, **Environment Providers** and their lifecycle, multi-format reporting, the bounded autonomous **Repair Loop**, and the four-state OpenSpec **Archive Gate**.
- `windows-build-validation`: The **Build** capability — MSVC/CMake toolchain discovery, Developer-environment activation, Debug/Release/clean/incremental builds, static analysis, compiler-diagnostics classification, and build summaries; runs the existing unit and fuzz `ctest` suites.
- `windows-install-and-service-validation`: The **Installer** and **Windows Service** capabilities — install/upgrade/repair/uninstall with post-conditions on install integrity, directory ACLs, registry, scheduled tasks, and services; and SCM lifecycle validation (registration, config, start/stop/restart, recovery, delayed start, service account, logs, Event Viewer).
- `windows-privilege-and-ipc-validation`: The **Privilege Validation** and **IPC Validation** capabilities — privilege/token/integrity/ACL/Authenticode validation with failure diagnostics; engine↔service validation (discovery, mutual auth, Authenticode pinning, heartbeats, recovery, idle disconnect, version compatibility, startup sequencing); and named-pipe/shared-memory IPC validation (creation, ACLs, handshake, snapshot publication/sync, session isolation, timeout/reconnect, protocol/malformed/large-payload).
- `windows-filesystem-and-runtime-validation`: The **Filesystem Validation**, single-session reliability, **Stress** (registered, Tier-3-gated), and **Performance** capabilities — filesystem validation (volume enumeration, NTFS traversal + permissions, USN journal handling and recovery, incremental indexing, rescans, staleness and stale-index recovery, very large directory trees, symlinks, junctions, reparse points, alternate data streams, long paths, deleted/renamed/moved/locked files); reliability (unexpected termination, engine/UI crash recovery, resource/handle/memory/thread-leak checks); and a historical performance-baseline store with configurable-threshold regression detection.
- `windows-ui-automation-validation`: The **UI Automation** capability (new spec) — UIA-driven, non-pixel verification of launch, directory navigation, multi-column interaction, keyboard/mouse input, connection-badge/dialog/scroll/search/error-state checks, and rendering-where-practical; registered now, Tier-2-gated (SKIPPED until an interactive UIA context is available).

### Modified Capabilities
(none — this change adds meta/tooling capabilities; it changes no existing product spec. It does unblock, but does not modify, the requirements in `establish-architecture-foundation`.)

## Impact

- **New repo tooling** under `verify/` (or `tools/verify/`): the PowerShell orchestrator core (registry, scheduler, gate, reporting), one module per **registered capability** implementing the shared versioned interface, capability/suite descriptors, environment-provider adapters, native `fftest.exe` runtime probes (for checks that must run inside a service/SYSTEM token or link the product libraries), and the run-artifact tree (incl. the historical performance-baseline store and crash-analysis artifacts).
- **Build system**: adds CMake presets (Debug/Release, `/analyze` variant) and a `fftest` target; reuses the existing `ctest` unit + fuzz targets. No product source behavior changes.
- **External tooling dependencies** (optional, availability-probed — absence yields `SKIPPED`, never failure): Debugging Tools for Windows (WinDbg/`cdb`, symbols), Windows Performance Toolkit (WPR/WPA), Sysinternals (ProcMon, ProcDump), Application Verifier/PageHeap, and hypervisor/sandbox/runner tooling for Environment Providers.
- **OpenSpec workflow**: adds a four-state archive-gate step consulted by the archive flow; does not alter the schema.
- **Execution environment**: assumes the agent runs on this Windows 11 host; Tier 0 runs as-is, Tier 1 obtains elevation on demand (elevated shell or a one-time approved scheduled task) and **always uninstalls in teardown** to leave the host clean. A dedicated snapshot-restorable VM remains an optional, more-isolated target the same contracts support later.
- **Security posture**: introduces an autonomous agent that installs services and rewrites ACLs on a real machine — deliberately bounded by an allowlisted verb set, scoped elevation, mandatory teardown, a rule never to disable product hardening to make a check pass, and the repair-loop gate invariant (see design.md).
