## Review — Lane D: WAL growth, checkpointing, crash consistency (read-only; no edits made)

### 1. Where WAL behavior is set, and the exact checkpoint strategy

- `src/indexstore/src/Store.cpp:777-780` — `Store::Open` runs `PRAGMA journal_mode=WAL; PRAGMA synchronous=NORMAL; PRAGMA foreign_keys=ON;` once per open. Nothing anywhere sets `wal_autocheckpoint` or `PRAGMA wal_checkpoint`; the amalgamation default (1000 pages) is compiled in (`third_party/sqlite/sqlite3.c:14858-59`, installed per connection at `:191061`). `busy_timeout` 250 ms is set **only on read sessions** (`Store.cpp:1703`); the writer handle has no busy handler.
- Checkpoint API (`Store.cpp:974-1012`): `CheckpointPassive()` = `sqlite3_wal_checkpoint_v2(PASSIVE)`; `CheckpointIfWalExceeds(t)` = PASSIVE first (reading `pnLog` frames), then if `frames × pageSize > t` escalate to **RESTART** (blocking, resets the log). Page size is real, cached (`Store.cpp:990-1005`).
- Who calls it: `IndexPipeline::RunStoreMaintenance` (`src/engine/src/IndexPipeline.cpp:520-533`) — passive then threshold check, then `VACUUM` only when idle. Callers: `VolumeSessionManager::ReconciliationSchedulerLoop` (`src/engine/src/VolumeSessionManager.cpp:1430`) on every scheduler wake — poll interval `kSchedulerPollInterval{10}` minutes (`:54`) plus lifecycle-event wakes (`:325/526/810/844/1000/1128`) — and the idle manager (`src/engine/src/Main.cpp:334-341`, `kIdleTimeout` = 10 min).
- **Threshold discrepancy:** production is `kWalForceCheckpointThresholdBytes = 4000ULL*4096` = 15.6 MiB (`IndexPipeline.cpp:334`, comment "~16 MB", task 1.6). The claimed "32 MiB threshold" exists **only as a literal in the bench** (`tests/indexstore/bench_candidate_index_resources.cpp:172/189/209/223/240/288`). `evidence/resource-measurements.md:5` calls the bench's 32 MiB "production checkpoint policy" — wrong on both value and cadence (P2). Also `Store.cpp:~993` comment "every 500ms during scan bursts" does not match the 10-minute/event-driven cadence (P2, stale comment).

### 2. Transaction boundaries of the mass-removal/replacement path

- **Bench** (`bench_candidate_index_resources.cpp:191-246`): mass-remove, reinsert, and ForgetVolume loops are chunked at 5000 rows per `ApplyBatch` (each = one `BEGIN IMMEDIATE…COMMIT`, `Store.cpp:1335-1455`), but `CheckpointIfWalExceeds` is called **once after each whole phase**, not per batch (contrast the ingest loop `:166-172`, `:284-288`, which is per batch). So the measured 960 MB/121 MB phases ran with only SQLite's default autocheckpoint — and the `resource-measurements.md` claim "applied at batch boundaries" is false for exactly the arms that produced 960 MB (P1-methodology).
- **Production is worse structurally**: `IndexPipeline::FinishReconciliationPass` (`IndexPipeline.cpp:1020-1077`) collects **all** not-seen/excluded row IDs into one vector and applies them with a **single `store_.ApplyBatch` = one giant transaction**. `Store::ForgetVolume` (`Store.cpp:1246-1303`) is likewise one transaction over the whole volume; `RebuildCandidateIndex` is one per-volume transaction (`Store.cpp:626-717`).
- **Quantification:** 2M rows × ~480 B of modified pages ≈ 960 MB exactly — consistent with single-transaction accumulation (production reconciliation) *and* with cumulative WAL frames never reset (bench, 400 commits ≈ 2.4 MB each ≈ 960 MB cumulative). The two arms' 960/121 MB ratio (7.9×) matches the measured FTS5-maintenance multiplier (3.5-9.7×). **Hypothesis:** in the bench, log restarts did not occur during remove/reinsert (default autocheckpoint backfills but the file only stops growing when the writer restarts the log — `walRestartLog`, `sqlite3.c:71393-71433`; the "uncheckpointed 376 MB" artifact shows cumulative growth between explicit checkpoints). This mechanism should be pinned by the §4 experiments rather than assumed; the arithmetic fit alone doesn't distinguish it.

### 3. Crash consistency: promise vs. proof

- **Promise:** `specs/index-engine/spec.md:51-63` — candidate index "SHALL be crash-consistent with the entries table… transactionally coupled"; `evidence/architecture-decision-record.md:40-41` — "crash consistency for free: index and entries commit atomically". `synchronous=NORMAL` loss-of-recent-commits is explicitly tolerated by resumable scan/journal (`Store.cpp:769-774`).
- **Proof:** `tests/indexstore/test_store.cpp:1149-1186` (fault mid-`ApplyBatch` → whole batch rolls back; reopen shows no phantom candidates) and `:1189-1228` (real `ExitProcess` inside an uncommitted batch → WAL recovery, atomicity, candidate consistency). Plus interrupted-migration kill/recovery (tasks 3.3). These are sound but at **10–100-row scale**.
- **Gaps (all operational, not correctness — SQLite WAL atomicity is size-independent):**
  - P1: no crash/interruption test during a mass-removal-scale transaction or chunked removal burst; no recovery-time or `integrity_check` bound at ~1 GB WAL (replay time is unmeasured — hypothesis: seconds to tens of seconds at 2M rows).
  - P1: no `SQLITE_FULL` behavior test. Disk exhaustion mid-giant-transaction rolls back cleanly, but `FinishReconciliationPass` retains the obligation on failure (`IndexPipeline.cpp:1064-1071`) and will re-run the same giant transaction — a retry loop that fails identically while free space stays low; the grown `-wal` file is not shrunk by rollback.
  - P2: RESTART escalation has no busy handler and concurrent `StoreReadSession` snapshots make it return `SQLITE_BUSY`; the result is discarded (`IndexPipeline.cpp:527`) — so under active readers the "forced" checkpoint silently doesn't force.

### 4. Minimal WAL experiment set (disposable DBs only)

Driver: `ffindexstore_bench_candidate_resources` (`RunLifecycleArm` already has `WalWatcher` 100 ms polling + A/B maintenance seam); crash arms reuse `test_store.cpp`'s `--hard-exit-child` pattern; reconciliation semantics via `ffengine_index_pipeline_tests`. 4. **Reconciliation-like update** — drive `FinishReconciliationPass` with a 2M-row seen-set diff (currently NOT_EXECUTED as a bench arm, per matrix) — expect ~1 giant-transaction WAL ≈ 960 MB regardless of checkpointing.
5. **ForgetVolume** at 2M — single-transaction WAL, recovery after kill mid-forget.

**Disk safety (forbid real exhaustion on system volume):** bound worst case arithmetically (480 B × rows + 2× margin) and add a free-space guard to `WalWatcher` (abort-and-record below 1 GB free). For true `SQLITE_FULL`, use a test-only fault-injection seam at commit (existing `SetTestingCandidateFault` pattern) or, opt-in only, a size-capped VHDX on a disposable data volume — never fill the system volume.

### 5. Recommendation

**Chunk large removal transactions + checkpoint at chunk boundaries** is the narrowly scoped fix: chunk `FinishReconciliationPass` removals (e.g., 5000 rows, matching bench granularity) with `CheckpointIfWalExceeds` after each chunk. It is safe: per-batch atomicity (the spec's promise) is unchanged per chunk; removals are derived and idempotent — partial progress plus a crash simply re-derives the rest on the next pass; projection updates follow each committed chunk. Expected: WAL peak ~15.6 MiB + one batch; wall time within noise of the linear 20 s baseline. Complementary small edits: honor RESTART failure (busy handler on `db_` or bounded retry), fix the P2 doc/comment claims (32 MiB vs 15.6 MiB; "batch boundaries"; "500ms"). A **free-space reserve document alone** does not fix `ForgetVolume`, per-volume rebuild/migration transactions, or the silent-RESTART-failure mode — but one should be documented regardless (worst-case WAL ≈ 480 B × rows-in-largest-transaction; ~1 GB at 2M).

**Evidence needed to decide:** §4 experiments 2/3/4/6/7 — (a) chunked vs unchunked peak WAL at 2M under production cadence; (b) RESTART failure rate with concurrent readers; (c) recovery + integrity time at ~1 GB WAL; (d) clean `SQLITE_FULL` failure/retry behavior. If (a) caps WAL <64 MB at unchanged throughput, chunking wins outright.

**Findings summary:** P1-meth: bench remove/replace arms checkpoint only per phase (`bench_candidate_index_resources.cpp:191-246`) contradicting `resource-measurements.md:5-6`. P1: production reconciliation is one giant transaction (`IndexPipeline.cpp:1038-1050`) — structurally ~960 MB WAL at 2M regardless of checkpoints. P1: no scale crash/`SQLITE_FULL` tests.
