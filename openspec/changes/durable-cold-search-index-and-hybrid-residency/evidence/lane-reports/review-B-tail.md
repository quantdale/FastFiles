Evidence-class note on the kill test: the seam fires at candidate op 5 of 100 (`test_store.cpp:1288`) — mid-batch, early, with no `COMMIT` in flight and few WAL frames written; "kill-during-commit" is a misnomer. `ExitProcess` is genuinely process-death-equivalent for WAL atomicity (skips rollback/close; committed frames survive via the OS cache) and the test comment honestly scopes it as "process-termination evidence" — but it evidences nothing about power loss (`synchronous=NORMAL`) or kills during the COMMIT statement itself.
### Verdict on transactional consistency
The entries↔candidate-index coupling itself is **correct by construction**: single-transaction maintenance with whole-batch rollback on any statement failure, marker-gated multi-transaction rebuild, and an idempotent, properly ordered v2→v3 bump. I found no path where entries commit without their candidate structures or vice versa. The one genuine transactional/migration defect is the **v1→v3 branch's non-idempotent ALTER-before-bump ordering** (P1), which can permanently brick open on an existing v1 database after a crash *or* an ordinary rebuild failure. The remaining P2s are verification/evidence gaps: the crash-consistency claims are true (they follow from SQLite WAL semantics) but weaker than the tests and comments assert, because the open-time repair masks the very state the tests claim to observe and the cross-check cannot see content-level staleness.
**Merge verdict: BLOCK** — land the two-phase version bump (v1→v2 bump immediately after the ALTER) before merge; the P2 evidence/verification items can follow as a focused second pass. Validation commands for the supervisor to run after any fix: `cmake --build --preset debug --target ffindexstore_tests` (or the exact test target name in `tests/indexstore/CMakeLists.txt`), then `ctest --test-dir build/debug -R indexstore --output-on-failure`, plus `ctest --preset debug` before submitting.
