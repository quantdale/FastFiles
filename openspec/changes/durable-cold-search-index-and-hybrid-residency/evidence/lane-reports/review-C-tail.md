 needles ("log", "tmp", "202") materialize the entire FTS match set through map→`WITHOUT ROWID` entries B-tree lookups, and the side-set union is **unbounded and unconditional** (`Store.cpp:1674` — `UNION SELECT term_rowid FROM entry_name_exceptions` has no count gate): on fold-exceptional-heavy corpora (e.g. CJK name volumes, where nearly every name is side-set) *every* eligible query streams effectively the whole volume, strictly worse than the sequential LIKE/GLOB scan (~1.05–1.10 µs/row measured floor). The hot planner refuses exactly this shape and falls back to scan (`Projection.cpp:973-976`, `988-991`, `1018-1021` vs `kMaximumFilenameIndexCandidates = 16*1024`, `IndexPipeline.h:399`). This is tracked-but-unimplemented acceptance truth: `openspec/changes/durable-cold-search-index-and-hybrid-residency/tasks.md:21` ("[ ] 3.2 Wire cost-based planner selection (candidate cap + fallback to canonical scan preserved)") and WORKSTATE "NEXT EXACT ACTION … cost-based planner refinement for broad classes". Smallest fix: cap the candidate rowid set (e.g. `LIMIT cap+1` probe or an exceptions-count pre-check) and fall through to the prefilter scan above a measured threshold — noting WORKSTATE's own caveat that the 16,384 value "does NOT transfer blindly" and broad shapes must be measured per class first.
- **Finding: P2 — mid-stream candidate-query failure re-streams through the fallback and delivers duplicate rows as "complete".** `src/indexstore/src/Store.cpp:1686-1687`: on `sqlite3_step` error *after* ≥1 row was visited, the code falls through to the LIKE/GLOB stream (`:1690-1717`), re-visiting those rows. `SearchAccumulator` does not dedup (`src/search/src/Search.cpp:224` push per admitted candidate), so the response contains duplicates while the stream returns `true` and `failed_` stays false. Trigger is narrow (real `SQLITE_IOERR`/`CORRUPT` surfacing mid-read — the `ShouldFail(Stream)` fault correctly returns `false` at `:1680-1683`, so tests don't exercise this path). Smallest fix: fall through only when zero rows were delivered; once any row was visited, mirror the prefilter loop's step-error contract (`failed_ = true; return false`, `:1716-1717`) to avoid silently wrong results.
- **Finding: P2 — the rung never re-checks `entry_name_index_meta` at query time; a cross-connection rebuild can under-report as complete.** `RebuildCandidateIndex` commits its DELETE-all + `state=0` before the per-volume rebuild commits and flips `state=1` last (`Store.cpp:580-660`), but `ForEachEntryWithAsciiNameUntil` (`:1658-1687`) trusts index state proven at `Store::Open` (`:775-801`) with no query-time consult. A concurrent read session on another connection (second logon session of the same user → second engine on the same DB file, or crash-recovery reopen racing a live reader) streaming mid-rebuild gets a partial candidate set that *succeeds* → silent false negatives — exactly the "empty candidate result ≠ broken index" failure mode. In-process races are defused (see Correct), so this is a genuine but narrow cross-process hole. Smallest fix: check `state==1 AND fold_signature=<host>` (cheap, cacheable per session) before taking the rung; fall back to the canonical stream otherwise.
- **Finding: P3 — foldedness precondition is enforced by naming/comment only.** The gate checks ASCII + length (`Store.cpp:1655-1657`) but not that the needle is actually folded; the rung's `case_sensitive 1` MATCH over `FoldAsciiUtf8` names would return **zero** candidates for e.g. `"Tmp"` while the LIKE fallback would have matched — a silent under-report for any future direct caller that skips folding (contract documented at `Store.h:262-268`; tests fold before calling, `test_store_read_session.cpp:455-461`; the current engine caller upholds it). Smallest fix: fold the needle in-function (it is already used to build the LIKE pattern too) or reject `A`–`Z` in the gate to fail-safe to the fallback.
- **Finding: P3 — no SearchTimings attribution for cold rung selection.** Hot accelerator has `filenameIndexUsed`/`filenameIndexCandidateCount` (`IndexPipeline.h:104-105`) but the cold path exposes only `storeStreamMs`/`coldRowsExamined` (`:110-113`); whether the FTS rung or the LIKE/GLOB fallback served a query is invisible to the benchmark seam, so the change's own acceptance item "measured planner decision quality (when index is consulted vs scan)" (`design.md` §3-5) cannot be evaluated on the cold path. Add a `coldCandidateRungUsed`-style flag alongside the P1 fix.
### Verdict on planner/fallback soundness
**Fallback soundness: OK** (conservative superset at every rung, failure lands on the canonical stream) with the P2 duplicate fall-through as the one exception where an error converts into silently duplicated "complete" results. **Planner soundness: incomplete** — the planner is *correct* (never misses rows) but not *cost-sound*: it has no cap, no cost model, and no fallback for eligible-but-broad needles, contradicting the hot path's `kMaximumFilenameIndexCandidates` philosophy and the change's own open task 3.2. Cancellation and visitor semantics are sound end-to-end.
**Merge verdict: BLOCK** — not for the code that exists (it is correct and well-tested: superset differential, migration, crash, tamper-rebuild all green), but because the named acceptance contract (tasks.md 3.2 cost-based planner selection) is unimplemented and the 2M/5M broad-class validation that would bound P1 is still owed; P2 duplicate fall-through should be fixed before this leaves the branch. If judged strictly as a mid-campaign WIP checkpoint where 3.2 is knowingly deferred to the next slice, this is "OK with notes" — but it must not be merged as a finished change.
