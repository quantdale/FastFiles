## Context

`establish-architecture-foundation` locked in native C++ (Win32 + COM + Direct2D/DirectComposition) and the three-process split (`FastFilesIndexSvc` / `FastFilesEngine` / `FastFiles`), and shipped read-only Column View browsing in `FastFiles` against `FastFilesEngine`'s degraded-mode directory listing. That foundation is explicitly non-goaled out of file operations ("File operations beyond read-only navigation (no copy/move/delete/rename yet)").

This change adds the ability to actually act on files from Column View: copy/cut/paste/move/rename/delete/create, conflict handling, and multi-selection/drag-and-drop. It is a UI-process-local concern:

- File operations run entirely inside `FastFiles.exe`, directly against the live filesystem via ordinary unprivileged Win32 APIs and the shell's `IFileOperation` COM API — exactly as any normal user-mode Explorer-class application would. This is a deliberate, explicit non-interaction with the privileged index machinery (`FastFilesIndexSvc`, `FastFilesEngine`'s MFT/USN path): raw MFT/USN reading is a read-side concern for search and storage analysis, unrelated to how bytes move on disk.
- Because this is native C++ with direct COM access — not a managed language crossing a COM-interop/RCW boundary — `IFileOperation`, `IDropSource`, `IDropTarget`, and `IDataObject` are consumed as native C-vtable COM interfaces with no marshaling tax and no wrapper-object lifetime quirks to manage.
- The one piece of cross-process awareness this change does own: after an operation completes, `FastFiles` SHALL notify `FastFilesEngine` of the affected paths so any cached index/snapshot entries for those paths are invalidated/refreshed on the next publish cycle. This is a one-way, best-effort notification over the existing same-privilege engine↔UI control pipe from D3 of the foundation design — it does not block the file operation's own completion, and its absence (e.g., engine not running) SHALL NOT fail or delay the file operation.

Primary invocation surface is `column-view-browsing` (per the proposal's Impact section): selection happens in a column, operations are invoked from context menu/keyboard/drag-drop on that selection, and results are reflected back into the column's item list. `navigation-and-workspace` (tabs, dual-pane) and `storage-analysis` will invoke the same capability later; this change does not build or modify those surfaces.

## Goals / Non-Goals

**Goals:**
- Copy, move, rename, delete, and create (file/folder) operations that never block the UI thread, regardless of item count or size.
- Recycle Bin as the default, unsurprising delete path; permanent deletion as a distinct, hard-to-misclick, explicitly confirmed action.
- Live progress (current item, overall percentage, transfer speed/ETA where the data is reliable) and user-initiated cancellation for any in-flight batch operation.
- A single, consistent, in-app conflict-resolution flow (replace/skip/auto-rename/apply-to-all-remaining) that looks and behaves like the rest of FastFiles, not like a native Explorer dialog dropped in.
- An operation history limited strictly to genuinely reversible operations (rename, move, Recycle-Bin delete), sufficient to drive an Undo command.
- A selection model (Ctrl-click/Shift-click/Ctrl+A) and native OLE drag-and-drop that behaves correctly both as a drag source and drop target against real Explorer windows.
- Non-crashing, clearly surfaced error handling for locked files, permission errors, and items that vanish between being listed and being acted on.

**Non-Goals (explicitly out of scope for this change):**
- Any navigation UI (address bar, tabs, dual-pane, bookmarks) — that is `navigation-and-workspace`.
- Any change to the index/snapshot pipeline itself — this change only emits an invalidation hint; how `FastFilesEngine` reconciles it is that capability's concern, unchanged here.
- Cross-machine/network-share-specific behavior beyond what `IFileOperation` already provides transparently (no custom UNC handling).
- Cloud-placeholder-file (Files-On-Demand/OneDrive) specific semantics beyond what `IFileOperation` already provides transparently — recognized as a general limitation, not solved here.
- Persisted, cross-session undo history — the history is in-process for this change (see D6); durable persistence is an open question, not a commitment.
- Redesigning `column-view-browsing`'s layout/rendering — this change only adds operation entry points and selection-state plumbing onto it.

## Decisions

### D1: Threading model — a dedicated STA "file-ops worker" thread owning `IFileOperation`

**Decision:** All `IFileOperation` use is confined to one dedicated, long-lived worker thread per `FastFiles.exe` process, explicitly initialized as `COINIT_APARTMENTTHREADED` (STA). The UI thread never calls `IFileOperation` methods directly and never blocks waiting on the worker. Requests (copy/move/delete/rename/create) are posted to the worker thread via a simple in-process queue (e.g., `PostThreadMessage`/a lock-free or mutex-guarded work queue drained by a message loop on that thread); the worker thread owns one `IFileOperation` instance per active batch, drives its `PerformOperations` call, and receives `IFileOperationProgressSink` callbacks on itself (COM guarantees STA callbacks arrive on the apartment's own thread via its message loop). The worker thread marshals progress/completion/error events back to the UI thread via `PostMessage`/window messages carrying plain data (paths, counters, HRESULTs) — never raw COM pointers — so the UI thread only ever touches UI-thread-owned state.

**Why an STA worker thread rather than calling `IFileOperation` inline on the UI thread:** `IFileOperation`'s built-in progress dialog (when used) and its internal marshaling both require an STA with an actively pumped message loop; calling `PerformOperations` synchronously on the UI thread for anything beyond trivially small operations would freeze window repainting, input, and Direct2D/DirectComposition presentation for the whole duration of a large copy/move — unacceptable for an app whose other pillars (instant search, Column View) are built around never blocking.

**Why a single dedicated worker thread rather than a thread pool / one thread per operation:** `IFileOperation` batches multiple items into one call by design (that's how it does its own internal grouping, single progress dialog, and "apply to all" semantics) — queuing operations onto one worker serializes them naturally and keeps exactly one COM apartment's lifetime to reason about. Concurrent operations (e.g., a copy still running while the user requests a delete elsewhere) are queued and processed in order rather than run in parallel, which avoids two `IFileOperation` instances racing on overlapping destination paths — a real correctness hazard, not just a performance one. If future profiling shows queuing hurts perceived responsiveness for unrelated concurrent operations (e.g., copy to drive A and delete on drive B truly don't conflict), a bounded small pool of worker threads (still each STA, still each owning its own `IFileOperation` instance) is the natural extension — tracked as an open question below, not built now.

**Alternatives considered:**
- *Call `IFileOperation` synchronously on the UI thread with `SetOperationFlags`/hourglass cursor.* Rejected outright — directly reintroduces the UI freeze this design exists to avoid.
- *One-shot MTA-initiated background thread per operation, without STA.* Rejected — `IFileOperationProgressSink` callback delivery and `IFileOperation`'s internal implementation are documented to require STA; using MTA risks callbacks not firing reliably or requiring proxy/stub marshaling overhead that defeats the "no marshaling tax" premise of the native-C++ decision.
- *Thread pool with one `IFileOperation` per submitted batch, run concurrently.* Rejected for this change on correctness grounds above; kept as a documented future option once operation-conflict detection exists.

### D2: Progress reporting via `IFileOperationProgressSink`

**Decision:** Every batch operation implements a single `IFileOperationProgressSink` (a small internal class, not per-item) registered via `IFileOperation::Advise` before `PerformOperations`. The callbacks actually used:

- `PostCopyItem` / `PostMoveItem` / `PostDeleteItem` / `PostNewItem` — fired after each item completes (success or failure via the `hrCopy`/`hrDelete`/etc. parameter); used to advance "current file" display and to record the completed source→destination mapping for undo history (D5) and per-item error collection.
- `PostRenameItem` — same, for rename batches.
- `UpdateProgress(iWorkTotal, iWorkSoFar)` — used for the overall progress bar. `iWorkSoFar / iWorkTotal` (both `UINT` work units `IFileOperation` itself computes from item sizes) drives the percentage; transfer speed is derived by the worker thread sampling `iWorkSoFar` against a wall-clock timestamp every ~250ms and computing a rolling-average bytes/sec, with ETA = remaining work units ÷ that rate. Speed/ETA are explicitly labeled as estimates and suppressed (dashes shown instead of a number) for the first ~1 second of an operation or whenever the rolling window has fewer than 2 samples, rather than showing a wild/meaningless early estimate.
- `PreCopyItem`/`PreMoveItem`/`PreDeleteItem`/`PreRenameItem`/`PreNewItem` — used only to update "current item" display (the name about to be processed) before the corresponding `Post*` confirms completion; not used to change flow control.

**Error surfacing without aborting the batch:** `IFileOperation` is configured (see conflict-resolution flow, D4) so that per-item failures — access denied, sharing violation from a locked file, a source item that vanished — do not abort the remaining batch by default. Each `Post*Item` callback whose HRESULT parameter is a failure code appends a `{path, HRESULT, phase}` entry to an in-memory per-batch error list; the batch continues. When the batch completes, the UI thread is handed the full error list alongside the normal completion event and renders a single non-blocking summary (e.g., "Copied 42 of 45 items — 3 failed, click for details") rather than interrupting the operation per-error with a modal. This mirrors modern Explorer's own "skip errors and report at the end" behavior rather than the older "stop on first error" model, and is a deliberate choice: a locked log file mid-batch should not block copying the other 44 items.

**Alternatives considered:**
- *Per-item modal error dialogs as they occur.* Rejected — defeats the entire point of an async, non-blocking batch operation and does not scale past a handful of errors.
- *Abort the whole batch on first error (`IFileOperation`'s more conservative historical default in some flag combinations).* Rejected as the default; too surprising for large batch operations where one locked file is common and unrelated to the other items.

### D3: Cancellation

**Decision:** The progress UI (owned by the UI thread, fed via the marshaled events from D1/D2) exposes a Cancel affordance. Clicking it posts a cancel request to the worker thread, which calls the standard cooperative-cancellation mechanism `IFileOperation` exposes for exactly this purpose (an `IOperationsProgressDialog`-style stop signal delivered by returning a stop indication from the progress sink / invoking the operation's own cancel entry point that `IFileOperation` polls between items and, where the underlying copy engine supports it, mid-item). `PerformOperations` then returns with a cancellation HRESULT; the worker thread treats every item that had already completed (per the `Post*Item` callbacks already received) as done and everything else as not-started, and reports a single "Cancelled — N of M completed" state rather than a hard error. Items that had already completed before cancellation are eligible for undo history exactly as if the batch had finished normally (D5); items in flight at the moment of cancellation are treated conservatively as not completed unless a `Post*Item` success callback was actually received for them.

**Why cooperative, not thread termination:** Forcibly terminating the worker thread mid-`IFileOperation` call is unsafe (COM/shell state left inconsistent, potential partial-file corruption) and is never used. Cancellation is always cooperative and always resolves to a clean, fully-accounted-for stopping point.

### D4: Conflict-resolution flow — custom in-app dialog, not native Explorer UI

**Decision:** `IFileOperation` is invoked with `FOFX_NOMINIMIZEBOX`-class flags and, critically, **without** `FOF_ALLOWUNDO`'s companion default conflict UI — instead each destination-name collision is detected up front and mediated by a FastFiles-owned custom dialog, styled consistently with the rest of the app (matching the Column View chrome, not the classic Explorer "Replace or Skip Files" window). Mechanically: before calling `PerformOperations`, the worker thread does a pre-flight pass over the requested copy/move item set, checking (via plain `GetFileAttributesEx`) which destination names already exist; for each conflict it invokes the same `IFileOperationProgressSink::PreCopyItem`/`PreMoveItem` callback pattern combined with `IFileOperation::SetOperationFlags(FOF_NOCONFIRMATION | FOF_NOERRORUI ...)` plus programmatic per-item response (`IFileOperation` supports "confirm and rename" resolution driven by the caller supplying an explicit destination name per item, which is how the custom dialog's decision is actually applied — either passing the caller's chosen new name for a conflicting item, or omitting that item from the batch entirely for Skip). Concretely, each conflicting item is queued into a small state machine: pause before that item, show the in-app dialog (Replace / Skip / Keep Both / with an "Apply to all remaining" checkbox), then resume the batch having chosen the destination name (auto-renamed, e.g. "file (2).txt") or omitted the item (Skip) or left it (Replace, i.e. proceed with the original destination name and let the copy overwrite).

**Why custom in-app UI over `IFileOperation`'s native conflict dialog:** the brief explicitly wants an integrated, consistent FastFiles experience, not native Explorer chrome popping up mid-operation inside an otherwise custom-rendered Direct2D/DirectComposition app — a jarring visual seam. A custom dialog also lets "apply to all remaining" be modeled explicitly and uniformly across the whole batch (see below) rather than relying on `IFileOperation`'s own "Do this for all current items" checkbox behavior, which is real but not visually or behaviorally consistent with the rest of the app.

**"Apply to all remaining" threading:** the conflict-resolution state carries one `ConflictChoice` (`Replace | Skip | KeepBoth`) plus an `appliesToAllRemaining` bool, held by the worker thread for the duration of the batch. Once a user checks "apply to all remaining" on any conflict dialog, every subsequent conflict in that same batch is resolved automatically using the stored choice without prompting again; this state is batch-scoped and reset for the next distinct operation the user initiates. See `conflict-resolution` capability spec for full behavior.

**Alternatives considered:**
- *Rely entirely on `IFileOperation`'s built-in conflict dialog (`FOF_ALLOWUNDO` default UI).* Rejected as the primary path — visually inconsistent with the app's custom chrome, and its "apply to all" semantics are per-`IFileOperation`-call rather than something FastFiles can style/control. Kept conceptually as a documented fallback only if a specific interoperability edge case (e.g., an item type requiring true shell-native negotiation) is discovered in implementation — not expected to be needed, not built by default.

### D5: Recycle Bin as default; permanent delete as a distinct action

**Decision:** The default Delete command (Del key, context-menu "Delete") invokes `IFileOperation::DeleteItems` with `FOF_ALLOWUNDO` set (the flag family that routes through the shell's own Recycle Bin machinery) — recoverable by design, matching user expectation from every other Windows file manager. Permanent deletion is a separate command, bound to Shift+Delete and a separate, clearly-labeled context-menu entry ("Delete permanently" — not just a modifier-key hint), which invokes the same `DeleteItems` path but explicitly without `FOF_ALLOWUNDO`. Permanent delete always shows a distinct, harder-to-misclick confirmation dialog: item count/name(s) stated explicitly, a non-default-focused destructive button (the default focus/Enter-key action is Cancel, not Delete), and copy that says "This can't be undone" rather than the milder Recycle-Bin-delete confirmation copy (which itself can be suppressed by user preference; the permanent-delete confirmation SHALL NOT be suppressible).

**Why:** matches the explicit brief requirement and universal user expectation that Delete is safe-by-default; permanent delete is rare and dangerous enough to warrant deliberate friction.

### D6: Undo model — in-memory operation history, strict inclusion invariant

**Decision:** `FastFiles` maintains an in-process, per-session (not yet cross-restart-persisted — see Open Questions) operation history stack. Only three operation kinds ever get pushed onto it: **rename**, **move**, and **Recycle-Bin delete**. Each history entry stores exactly what's needed to reverse it:
- Rename: `{originalName, newName, parentPath}` → reversed by renaming back.
- Move: `{sourcePath, destinationPath}` per item → reversed by moving back (itself performed as a normal tracked move-in-reverse, invoking `IFileOperation` again through the same worker-thread path — not a special code path).
- Recycle-Bin delete: `{originalPath, recycleBinItemIdentifier}` per item (the identifier `IFileOperation`/`IFileOperationProgressSink::PostDeleteItem` provides for the now-recycled item) → reversed via the shell's restore-from-Recycle-Bin operation (`IFileOperation` on the recycled item with a "restore" semantics, or the equivalent `SHFileOperation`-era restore path) targeting the original location.

**Hard invariant, stated explicitly and enforced structurally (not just documented):** permanent delete and "Replace" conflict resolutions (any operation that overwrites an existing destination item, destroying its prior content) are **never** pushed onto this history, under any circumstance. There is no configuration flag, no "advanced mode," and no future extension point that adds them — the history-recording code path structurally only has call sites for rename/move/Recycle-Bin-delete completions; permanent-delete and overwrite completions have no corresponding history-push call at all, so there is nothing to accidentally enable. Reasoning: both destroy data in a way this application cannot reconstruct (permanent delete bypasses the Recycle Bin entirely; an overwritten file's prior bytes are gone), so recording them in an "Undo" stack would actively lie to the user about recoverability.

**Alternatives considered:**
- *Best-effort overwrite undo via a shadow-copy of the replaced file before overwrite.* Rejected for this change — adds real complexity (extra disk I/O and space on every replace, unclear retention policy) for a safety net that conflicts with the explicit brief instruction to treat this as a hard invariant, not a nice-to-have; revisit only if a future change explicitly re-scopes this.

### D7: Drag-and-drop — native OLE `IDropSource`/`IDropTarget`/`IDataObject`, CF_HDROP

**Decision:** FastFiles implements native OLE drag-and-drop as a first-class COM surface, not a hand-rolled mouse-tracking approximation:
- `FastFiles` windows register themselves as OLE drop targets (`RegisterDragDrop` on the relevant Column View HWND) implementing `IDropTarget` (`DragEnter`/`DragOver`/`DragLeave`/`Drop`), reading `CF_HDROP` (and falling back to the Shell ID List Array clipboard format when a source only offers that) from the incoming `IDataObject` to obtain source paths.
- Dragging *out* of a FastFiles column is implemented via `IDropSource` plus a `IDataObject` implementation that exposes the selected items as `CF_HDROP` (`DROPFILES` structure with real filesystem paths) — the same format every native Explorer window and most Windows apps expect — so drops into real Explorer windows, other FastFiles windows, and third-party apps all work without any FastFiles-specific negotiation.
- The actual data movement once a drop is accepted reuses the same `IFileOperation`-on-the-worker-thread path as any other copy/move (D1) — drag-and-drop is a UI gesture that resolves to a normal tracked copy or move operation, including going through conflict resolution (D4) and undo history (D6) identically to a keyboard/menu-initiated copy or move.
- Effect (copy vs. move vs. link) follows standard Windows convention: Ctrl forces copy, Shift forces move, Ctrl+Shift forces link (shortcut), no modifier defaults to move within the same volume and copy across volumes — mirrored from `IDropTarget::DragOver`'s `pdwEffect` negotiation, not reinvented.

**Why native OLE COM interfaces, not a managed drag-drop wrapper:** this is native C++ with direct COM access — `IDropSource`/`IDropTarget`/`IDataObject` are implemented as ordinary C-vtable COM classes (a `QueryInterface`/`AddRef`/`Release` implementation plus the interface's own methods), with no interop marshaling layer, consistent with the same rationale D1 gives for `IFileOperation`. This is also the only implementation approach that guarantees correct two-way interoperability with real Explorer windows, since Explorer itself is a native `IDropTarget`/`IDropSource` implementation and any non-native approximation risks subtly wrong clipboard-format or effect-negotiation behavior.

**Alternatives considered:**
- *Custom in-process-only drag affordance (e.g., a synthetic overlay window tracked via mouse messages, dropping only understood by FastFiles itself).* Rejected — explicitly fails the requirement that dragging into/out of real Explorer windows must work in both directions.

### D8: Multi-selection model

**Decision:** Each Column View pane (and, later, each pane in `dual-pane-mode` from `navigation-and-workspace` — not built here, but designed not to conflict) owns one independent selection state: a set of selected item indices/identifiers plus a "selection anchor" and "focus" index, following the same convention as Explorer's list views:
- **Click** (no modifier): clears the pane's selection, selects only the clicked item, moves both anchor and focus to it.
- **Ctrl-click**: toggles the clicked item's membership in the selection without affecting any other selected item; moves focus (not anchor) to the clicked item.
- **Shift-click**: selects the contiguous visual range between the current anchor and the clicked item (replacing any prior range-selection from the same anchor), without clearing selections made in a different pane.
- **Ctrl+A**: selects every item currently visible/listed in the active (focused) pane only — never across panes, never across unloaded/not-yet-listed items in collapsed hierarchy.
- Selection is scoped strictly to one column/pane at a time; selecting in a newly-populated child column does not implicitly clear or merge with the parent column's own (now non-terminal) selection highlight — consistent with `column-view-browsing`'s existing "deepest active selection is identifiable" requirement from the foundation spec. This change does not alter that existing requirement; it adds the interaction model (Ctrl/Shift/Ctrl+A) on top of the single-item selection the foundation change already established.

File operations (copy/move/delete/rename/drag-start) always act on "the current selection in the active pane" as their input set; a single selected item is simply the degenerate one-item case of the same model. This keeps the operations capability decoupled from exactly how many panes/tabs exist — it consumes one selection-set contract regardless of whether that pane later belongs to a single-column view, a future dual-pane view, or a future tabbed view.

**Alternatives considered:**
- *Global cross-pane selection (one selection set spanning all panes/tabs).* Rejected — does not match Explorer convention, and would make an eventual dual-pane copy-between-panes gesture ambiguous (which pane's selection is "the source"?).

## Risks / Trade-offs

- **[Risk] A single serialized worker thread means a large copy can delay the start of a subsequently requested, unrelated operation (e.g., delete on a different drive) until the queue drains.** → **Mitigation:** operations are still individually cancellable and the UI clearly shows "queued" vs. "in progress" state; a bounded worker pool is a documented, low-risk future extension (see D1) if this proves to matter in practice.
- **[Risk] Pre-flight conflict detection (D4) followed by a caller-driven per-item destination-name resolution is more implementation complexity than simply delegating to `IFileOperation`'s own native conflict UI.** → **Mitigation:** accepted deliberately for UI consistency per the brief; the state machine is scoped per-batch and the logic is fully unit-testable independent of actual `IFileOperation` calls (fake destination-existence checks).
- **[Risk] Cooperative cancellation means an operation cannot be stopped instantly mid-large-file-copy; the current file may still finish.** → **Mitigation:** documented as expected behavior in the progress UI ("Cancelling — finishing current file…") rather than presented as an error; consistent with how Explorer itself behaves.
- **[Risk] Recycle Bin restore identifiers and behavior can vary subtly across Windows versions/shell builds.** → **Mitigation:** undo-of-delete is implemented against the documented shell restore mechanism only (no raw `$Recycle.Bin` manipulation); if restore ever fails (e.g., Recycle Bin was emptied out-of-band by the user), the Undo action surfaces a clear, non-crashing "can no longer be undone" message rather than silently no-op'ing or corrupting other history entries.
- **[Risk] `IFileOperation`/OLE drag-drop behavior with cloud-placeholder files (Files-On-Demand) and long/reserved-character paths has known Explorer-level quirks not fully controllable by a calling application.** → **Mitigation:** explicitly a non-goal for this change (see Non-Goals); errors surfaced through the same non-crashing per-item error path as any other failed item (D2), not specially handled.
- **[Risk] The in-memory undo history is lost on process exit/crash, and permanent-delete/overwrite are structurally excluded from it — some users may expect broader undo coverage than is provided.** → **Mitigation:** deliberate, brief-mandated invariant (D6); UI copy for permanent-delete/overwrite confirmations explicitly states the action cannot be undone, so the limitation is disclosed at the moment of action rather than discovered later.
- **[Risk] The engine-invalidation notification (Context) is best-effort/fire-and-forget; if `FastFilesEngine` is unreachable, cached index entries for just-modified paths can go briefly stale.** → **Mitigation:** acceptable by design — `FastFilesEngine`'s existing `ReadDirectoryChangesW` watches (from the foundation change) independently observe the same filesystem change and self-correct shortly after, so this notification is a latency optimization, not a correctness dependency.

## Migration Plan

Greenfield capability — no existing file-operations code or persisted state to migrate. `column-view-browsing` gains new context-menu entries, keyboard shortcuts, and drag-drop registration as additive UI surface; no existing requirement in that capability's spec is modified. No rollback-of-data concerns apply since no durable state format is introduced (the undo history is in-memory only per D6).

## Open Questions

- **Cross-session/persisted undo history:** whether the operation history should survive a `FastFiles.exe` restart (e.g., a small on-disk log) is left open; the in-memory-only model in D6 is sufficient for this change and doesn't block it, but is called out as a plausible follow-up.
- **Worker-thread pooling:** whether a single serialized STA worker is sufficient in practice or a small bounded pool (with explicit destination-path-overlap conflict detection between concurrently running operations) is needed is left for post-implementation profiling, per D1.
- **Fallback to `IFileOperation`'s native conflict UI for edge-case item types** that a pre-flight `GetFileAttributesEx`-based conflict check cannot cleanly classify (e.g., certain reparse points, cloud placeholders mid-hydration) is noted in D4 as a possible narrow escape hatch, not committed to.
- **Precise mapping of `dual-pane-mode`'s eventual two-pane selection/active-pane semantics onto D8's per-pane selection model** is intentionally left to `navigation-and-workspace` when that capability is built, since dual-pane doesn't exist yet; D8 is written to not conflict with it but does not fully specify it.
