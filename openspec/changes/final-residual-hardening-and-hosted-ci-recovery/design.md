## Context

See [proposal.md](proposal.md) for motivation and [the residual certification spec](specs/residual-certification-integrity/spec.md) for the observable contract. The supplied `a8533a772048ea39ad44c319a96ee91dc844506f` SHA is a historical starting observation, not a fixed implementation target. The existing residual change's task 1.4 remains unchecked. `ffipc::WriteFrameOverlapped` serializes a complete header and payload into one buffer, while `WriteExactOverlapped` advances through short writes. `ReadFrameOverlappedDetailed` reads header and payload separately and treats a partial payload timeout as a lost frame boundary. The current scanner test covers a closed-reader terminal write, not selected partial byte counts. `verify/core/Provenance.psm1` records binary SHA-256, embedded commit identity, source commit/tree, and clean state, but its strict binding currently ignores some binary-record failures; its own comment says the tree is not separately embedded. Current CI defines three build matrix entries plus ASan, hygiene, and release qualification. All historical results require fresh checking before certification.

The process and security constraints come from `openspec/changes/establish-architecture-foundation/design.md` D2–D4 and its Risks section: named pipes are the privilege boundary, the service is a constrained broker, commands are closed, handles are connection scoped, and authentication is symmetric. The earlier residual design's transport-fatal decision remains in force; this change supplies direct partial-write proof and changes product code only if that proof exposes a defect.

## Goals / Non-Goals

**Goals:**

- Exercise the serialized frame and real byte stream at deterministic cut points, including receiver and next-connection observations.
- Reach a documented, test-backed provenance decision without assuming that another embedded digest improves assurance.
- Bind local and hosted claims to actual candidate identity and evidence, then hand off exact external prerequisites.

**Non-Goals:**

- Rebuild the IPC architecture, extend the wire command set, or relax authentication, service ACLs, signing pins, or validation gates.
- Provision certificates, alter billing or payment settings, reconfigure displays, or claim production MFT/USN validation from a local test fixture.
- Reopen completed UI, visual, or prior certification campaigns without a new reproducer.

## Decisions

### D1 — Baseline is live state, not the supplied checkpoint

**Why:** The prompt's SHA, counts, and billing annotation are historical. Before implementation, capture current branch, HEAD, upstream, `origin/main`, tracked/untracked status, worktrees, concurrent activity, workflow, and existing tasks. Reconcile any advance without resetting. Preserve unrelated files and use the prior task 1.4 as the known uncovered behavior. **Alternative:** Treat `a8533a7` as authoritative and replay old certification; rejected because it could certify stale code. **Trade-off:** Fresh state collection takes time but prevents false exact-SHA claims.

### D2 — Inject a real byte prefix at the narrow transport write boundary

**Why:** A closed reader proves a failed write but not which bytes were emitted. The focused IPC fixture now uses the production serializer, frame validation, and connected byte-mode named pipes. Its test-only write seam caps a real Win32 write at a selected offset and fails the next operation; the fixture compares observed bytes with production read status. The seam is compiled only for `ffipc_framing_tests`, and normal production calls retain the same Win32 path. **Alternatives:** Timing-dependent reader closure is nondeterministic; a test-only serializer would not prove production bytes; rewriting `ffipc` is disproportionate. **Trade-off:** The seam adds a test-only branch at the write completion boundary, guarded from production builds.

The observed boundary matrix is zero bytes; partial header; complete header; partial payload; and all but the final byte. Scanner fixtures reach the production batch sender through a synthetic source, then invoke the same `RunScanWorkerBoundary` used by the service. Batch and terminal write failures are transport-fatal and do not append a later terminal. The service worker owner requests synchronous-I/O cancellation before joining; a real blocked named-pipe read through that owner fixture exits within its test deadline. A volume handle uses RAII through exception unwinding. Engine fixtures close the failed connection, observe no success callback and cleared retry/session state, then exercise a fresh test-only verifier decision; the test build policy checks that production still calls the pinned verifier. These fixtures do not claim live signed-peer or elevated MFT/USN validation.

Windows cancellation APIs mark synchronous requests for cancellation but do not wait for every operation to finish; some operations can continue toward completion. Thus the bounded result is proven for the cancelable service-pipe read fixture, while an arbitrary synchronous raw-volume `DeviceIoControl` still has no proven finite completion bound. The service requests cancellation and joins rather than detaching a privileged worker or freeing state it may still use. This limitation remains explicit and is not represented as a platform guarantee. `ScanFailed` retries are intentionally unlimited in attempt count, with a five-second per-volume cadence and one pending slot per active volume; disconnect and stop clear those slots. The tested bound is retry rate/state cardinality, not total attempts.

### D3 — Make provenance a threat-model decision gate

**Why:** Direct gate tests reproduced fail-open behavior for required binary-record issues and independent provenance reviews found additional path races: signature/version/hash facts could come from different reads, package/helper archive bytes could diverge from validated inputs, undeclared candidate output could enter an otherwise self-consistent archive, and the archived kit manifest could carry unvalidated privileged pin data. The strict binding now propagates collector issues, rejects empty/missing/malformed records and hash/version/PE failures, enforces the embedded build-time cleanliness claim, and reports `boundToTree=false` with `treeBindingStatus=NOT_EMBEDDED`. Release artifact records are read from one guarded snapshot; candidate creation validates the exact staged member allowlist and dependency inventory, recomputes the full kit-manifest projection from package/version/signature/pin facts, revalidates package and helper provenance, and verifies every completed ZIP entry against the snapshot inventory. Before success it verifies the generated manifests, checksums, archive, and a final output inventory after checksum enumeration. Child tools are captured so JSON mode emits only the candidate's terminal document; tests cover child PASS followed by a post-kit failure. The ZIP is the sole authoritative release payload, and the result includes its path and SHA-256 so consumers can detect replacement after return. The loose package directory and sidecar reports are mutable companion evidence, not a trust anchor, and extra siblings are never payload. The gate also inspects the caller-selected `BuildRoot`, requires the mode-specific configuration for all required binaries, checks the artifact-manifest configuration, and rejects production `-SkipVerification`. Negative tests exercise these defects. The threat matrix and evidence-backed decision are in `evidence/provenance-digest-decision.md`.

The selected-root binary hashes and package manifest prove the exact executable bytes and package-copy consistency. They do not prove which compiler, generated files, SDK, libraries, or other build inputs produced those bytes. Repository cleanliness and embedded commit identity are narrower claims. Ignored/generated files remain outside ordinary Git status, and no build-input attestation or reproducible-build verifier is present. A source digest would only attest the exact declared file set and would not independently tie the compiler's inputs to the resulting PE; adding one now would not close a reproduced authoritative-gate bypass. The recorded decision is `NOT JUSTIFIED`. **Alternative:** Add an embedded tree digest unconditionally; rejected because it would not repair the collector's former fail-open paths or prove compiler inputs. **Trade-off:** The direct repairs close demonstrated verifier defects while explicitly retaining build-input and toolchain provenance as separate future certification work.

If triggered, the digest design must fix included and excluded files, normalized paths, ordering, per-file content hashing, clean/untracked treatment, generated inputs, configuration/toolchain scope, and an independent verification point. Avoid a digest cycle through the binary containing itself. Negative checks cover modified/missing inputs, malformed or wrong digest, mixed and stale binaries, and dirty-state mismatch. Documentation must state exactly which claim the digest supports; a digest generated from the same selected build inputs is still self-asserted without independent verification.

### D4 — Certify hosted jobs only from the final pushed SHA

**Why:** The current workflow's required six executions are debug, release-test, analyze, ASan protocol/IPC/lifecycle, repository hygiene/contracts, and unsigned release candidate qualification. Confirm the live workflow and GitHub run state first. `verify/Invoke-CiParity.ps1` currently writes a fixed billing classification and old last-green run into every local report; replace that dated claim with a neutral local-only status or independently verified hosted evidence with run identity and observation time. If an account-level annotation still blocks job startup, record the run and exact text, avoid repeat dispatches, and classify hosted CI externally blocked. Once available, trigger or observe an authorized run for the final pushed SHA and inspect each job, skip, and required artifact. **Alternative:** Use local parity or workflow aggregate status as hosted proof; rejected because neither proves all hosted jobs executed successfully. **Trade-off:** Hosted closure remains external if the account cannot start jobs.

### D5 — Validate by candidate and review by independent attack surface

**Why:** The final implementation candidate needs focused tests first, then the complete applicable local ladder from the prompt: debug and release-test CTest, Analyze, ASan protocol/IPC/listener lifecycle plus the scanner worker-boundary fixture, strict OpenSpec, CI parity, identity/provenance negatives, archive-entry mutation checks, governance contracts, UIA/E2E, visual catalog, hygiene, and documentation drift. Preserve actual skips and bind retained evidence to the candidate's commit and tree. If a later documentation-only commit changes HEAD, distinguish that tip from the executable candidate: `Test-BinarySourceBinding` requires embedded identity to equal the source HEAD, so executable-tree equivalence alone cannot be reported as a fresh strict binding result for the new tip. Independent reviewers separately attack transport failure, provenance, certification truth, and regression/scope; each finding needs a reproduction or source-backed explanation. **Alternative:** Rely on historical green counts; rejected because relevant source edits invalidate them. **Trade-off:** Full certification is expensive, so implementation iterations use focused validation before the final ladder.

### D6 — External handoff uses existing certification infrastructure

**Why:** Production signer and pins, clean host, elevated MFT/USN, and display configurations require capabilities outside ordinary development. Inventory the canonical commands and expected evidence already present in `verify/` and report which prerequisite unlocks each. Vendor-specific disposable-guest execution is owner-excluded by the current handoff scope and is not reopened here. Do not create replacement infrastructure or call a missing scenario passed. **Alternative:** Rebuild a campaign around external gates; rejected by the supplied scope and existing harness coverage. **Trade-off:** Local residual closure can be complete while external certification stays open.

## Risks / Trade-offs

- **[Risk] Injected short writes bypass real serialization or completion semantics.** → Inspect the actual prefix on a named pipe, invoke production read code, and keep injection at the write operation rather than a replacement frame builder.
- **[Risk] A partial frame blocks the receiver or leaves an overlapped worker live.** → Use bounded framing deadlines, make service close the failed pipe to wake the engine's otherwise indefinite active read, and assert worker/handle cleanup; report a timeout as failure, never silently retry the same byte stream.
- **[Risk] A synchronous raw-volume IOCTL does not finish after a cancellation request.** → Request cancellation for the owned service worker and prove the cancelable pipe-read path; retain the arbitrary-driver completion bound as unproven, since cancellation APIs do not wait for completion.
- **[Risk] A portable service fixture appears to certify production authentication or raw MFT/USN.** → Keep verifier and scan-source seams confined to a test target, verify production linkage, exercise denied peers, and report live signed/elevated validation separately.
- **[Risk] A source digest is mistaken for a build attestation or masks an existing fail-open verifier.** → Repair required binary-record failures directly, state the precise remaining mismatch a digest closes, and keep binary hashes, build inputs, and compiler provenance separate.
- **[Risk] New commits make a previously certified SHA stale.** → Rebuild and rerun affected gates on the final candidate, compare tree identities, and inspect hosted jobs for the pushed SHA.
- **[Risk] External blockers tempt a local pass to be promoted to hosted or production success.** → Maintain explicit `BLOCKED_EXTERNAL` and scenario skip classifications and include exact unlock actions.

## Migration Plan

No wire or on-disk migration is expected. Land focused implementation commits, certify the final source candidate, then commit the evidence handoff with executable-tree equivalence documented if only documents change. Keep the certified executable SHA separate from a later documentation tip; rebuild and rerun strict binary-to-HEAD binding before claiming the latter is itself strictly bound. Revert a faulty fixture or optional digest through an ordinary corrective commit; preserve history and revalidate the affected candidate. Do not force-push or alter repository security policy.
