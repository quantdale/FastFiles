- [x] 1.1 Add SQLite as a bundled/statically-linked dependency of `FastFilesEngine`, opened in WAL journal mode with `synchronous=NORMAL`. (vendored amalgamation in `third_party/sqlite`, `ffindexstore::Store::Open`)

## 8. Reconciliation Sweeps

- [x] 8.1 Implement a per-volume reconciliation sweep that compares persisted entries against current ground truth (fresh scan or filesystem walk) and reports additions, removals, and stale-field updates. (a from-scratch `StartVolumeScan` pass; `IndexPipeline::BeginReconciliationPass`/`FinishReconciliationPass` anti-joins the pass's observed-FRN set against the durable store to find removals, while additions/stale-field updates fall naturally out of the pass's normal upserts)
- [x] 8.2 Implement idle-time/low-I/O-priority scheduling and pacing for reconciliation sweeps so they don't degrade foreground responsiveness. (`VolumeSessionManager::TriggerReconciliation` marks reconciliation scans low priority; the service's corresponding `VolumeScanner` worker enters `THREAD_MODE_BACKGROUND` and yields periodically while processing records, while normal initial scans and journal readers retain normal priority.)
- [x] 8.3 Implement periodic automatic scheduling of reconciliation sweeps per available volume (configurable interval), requiring no user-initiated manual rescan. (`VolumeSessionManager::ReconciliationSchedulerLoop`; interval is a fixed constant today, not yet exposed as user-configurable)
- [x] 8.4 Ensure reconciliation sweeps reuse/update existing (volume identifier, `FileReferenceNumber`) rows rather than deleting and recreating a volume's entire entry set. (the pass applies via the same `ApplyMftBatch`/upsert path as any other scan; only entries never observed during the completed pass are removed)
- [x] 8.5 Skip scheduling privileged-path reconciliation while the engine is in degraded mode; resume scheduling once the privileged connection returns to `Active`. (`ReconciliationSchedulerLoop` checks `active_` every poll)

Note: sections 3/6/7/8's engine-side code (`IndexPipeline.cpp` aside, which is portable and unit-tested in `tests/engine`) touches `windows.h` (`PrivilegedConnection.cpp`'s reader-thread refactor, `VolumeSessionManager.cpp`, `VolumeIdentity.cpp`'s `UuidFromStringW`/`GetVolumeNameForVolumeMountPointW` usage, `Main.cpp`'s `SHGetKnownFolderPath`) and is likewise unverified by an actual Windows build in this sandbox -- reviewed carefully by hand against the documented Win32 APIs, but needs a real compile and a multi-volume manual test (plug/unplug a removable drive, force a journal recreation, kill the engine mid-scan) before being trusted.

## 9. Testing and Validation

- [x] 9.1 Test crash-recovery: kill `FastFilesEngine` mid-ingestion-batch and verify WAL replay recovers a consistent database on restart with no permanently-lost committed data. (proxy test: `tests/indexstore/test_store.cpp`'s `TestWalReplayRecoversCommittedDataWithoutAnExplicitCheckpoint` commits via `ApplyBatch` then destroys the `Store` with no checkpoint, verifying reopen recovers it; a literal `kill -9` mid-batch against the real `FastFilesEngine.exe` process is not exercisable in this sandbox)
- [x] 9.2 Test resumable scanning: interrupt an initial volume scan partway through, restart, and verify it resumes from the persisted cursor rather than from zero, with no duplicate or missing entries in the final result. (covered at the `IndexPipeline`/`Store` level: cursor persistence, and idempotent re-ingestion of an already-committed FRN, are both unit-tested; the end-to-end "actually stop `VolumeScanner` partway and resume against a real volume" scenario needs a Windows run)
- [x] 9.3 Test volume disconnect/reconnect: remove and reattach a volume (or simulate via a test double), verifying entries are retained-but-marked-unavailable while disconnected and correctly resumed or reconciled on reconnect. (`tests/engine/test_index_pipeline.cpp` verifies availability changes retain entries; `tests/engine/test_volume_session_manager.cpp` simulates the reconnected session's journal-open callback and verifies a matching journal resumes the persisted position, while the changed-journal case is covered by 9.4.)
- [x] 9.4 Test journal discontinuity handling: simulate a recreated/invalidated USN journal and verify the engine falls back to reconciliation rather than silently missing changes or blindly resuming. (`tests/engine/test_volume_session_manager.cpp` drives `VolumeSessionManager`'s registered `JournalOpened` callback: a matching ID retains `ResumeUsn`, while a changed ID resets to the reported current position and begins a reconciliation pass.)
- [x] 9.5 Test symlink/junction cycle safety: construct a junction whose target is an ancestor of itself and verify scanning terminates normally with exactly one entry per physical MFT record, and that path reconstruction does not loop. (`tests/indexstore/test_projection.cpp`'s `TestCycleDoesNotCauseInfiniteWalk`)
- [x] 9.6 Test reconciliation self-correction: simulate a missed create and a missed delete event (e.g., by making a filesystem change while the engine's journal watch is paused) and verify the next sweep corrects both. (missed-delete: `TestReconciliationRemovesEntryNotSeenInFullScan`; missed-create isn't a separate code path -- a create the pass observes for the first time is just a normal `Upsert`, already covered by every other `ApplyMftBatch` test)
- [x] 9.7 Benchmark in-memory projection RAM usage at a representative large-volume entry count (several million entries) to confirm the interned-name/parent-reference design meets a reasonable memory budget compared to a naive per-entry-full-path baseline. **Result: it does not currently meet that budget.** A 5M-entry synthetic benchmark (10 recurring names, ~32 entries/directory, measured via process RSS delta) measured **~161 bytes/entry** -- worse than design.md's own ~100-byte naive-full-path estimate, not the ~40-50 bytes/entry target. Root cause identified: `idToIndex_` (`std::unordered_map<EntryKey, uint32_t>`, needed to resolve an externally-supplied FileId from a scan/journal batch to its projection slot, and to walk a parent chain by FileId) duplicates the full 24-byte `EntryKey` per entry plus `std::unordered_map`'s per-node pointer/allocation overhead, roughly doubling `entries_`'s own footprint on top of it. **Follow-up needed:** replace `idToIndex_`/`parentToChildren_` with an open-addressing (flat, no per-node heap allocation) hash structure before this design's memory claim can be trusted at scale; not implemented in this change given time constraints, but the gap is now measured and documented rather than assumed away.
- [x] 9.8 Verify MFT attribute allowlisting end-to-end: confirm no `$DATA` bytes (including resident small-file content) ever appear in engine-ingested records or the durable store. (`tests/indexsvc/test_mft_parser.cpp`'s `TestResidentDataAttributeIsNeverSurfaced`; also structurally true since `ParsedMftRecord`/`EntryRecord` have no field capable of carrying arbitrary attribute payload)
