## Context

`establish-architecture-foundation` shipped `column-view-browsing`: a single Finder-style multi-column navigation surface inside `FastFiles`, reading directory listings through `FastFilesEngine`'s degraded-mode (and eventually privileged-mode) directory data, delivered to the UI process via a read-only, double-buffered memory-mapped snapshot with generation-change notifications over a same-privilege control pipe. That work deliberately shipped exactly one navigation surface, showing exactly one location, with no history, no tabs, and no bookmarks — those were explicitly named as out of scope (see that change's proposal, "Explicitly out of scope").

This change (`navigation-and-workspace`) builds the conventional file-manager chrome around that surface: an address bar (breadcrumb and editable-text modes), back/forward history, tabs, dual-pane mode, and a sidebar combining drives, auto-discovered known folders, and user-managed bookmarks. None of this modifies `column-view-browsing`'s requirements — it adds sibling capabilities that each host one or more instances of column-view-style navigation state and coordinate which path each instance is showing.

The core architectural question this design must answer is: when the UI process now needs to show N independent locations at once (one per tab, times up to 2 panes in dual-pane mode), does each of those N "views" need its own connection to `FastFilesEngine`, or can they share one? The foundation's snapshot design (D3 in that change's design.md) was built precisely so that reads are in-process and connection-free after the initial map — this change's design leans on that directly rather than re-deciding it.

This change also introduces the first pieces of durable, per-user local state the product has (bookmarks, recently-closed tabs, possibly last-session tabs) — `establish-architecture-foundation` explicitly deferred all persistent user data ("no rollback-of-data concerns apply since this change introduces no persistent user data yet"). This design has to pick a storage shape for that, independent of the (still-open, per that change) index-storage-shape question, since bookmarks are a tiny, purely-local, non-filesystem-index concern.

## Goals / Non-Goals

**Goals:**
- Define a per-navigation-context state model (current path, column/selection state, back/forward history) that is independent per tab and per pane, while sharing a single `FastFilesEngine` connection and a single mapped snapshot per UI process.
- Design the address bar's two modes (breadcrumb, editable-text), how a user moves between them, and how pasted/typed path text is parsed, validated, and turned into either a successful navigation or a clear, non-crashing error state.
- Define what counts as a "navigation event" for back/forward history purposes, and confirm history is per-tab, never shared or merged across tabs.
- Define how known folders (Desktop, Documents, Downloads, Pictures, Videos, Music, etc.) are discovered via `SHGetKnownFolderPath`/`IKnownFolderManager`, how that differs from user-added bookmarks, and how both are surfaced in one collapsible sidebar alongside drives.
- Define dual-pane mode's relationship to tabs: whether each pane gets its own tab strip or is a single simplified context, with a justified MVP call.
- Define where and how bookmarks/favorites and recently-closed-tab history are persisted locally.

**Non-Goals:**
- Re-specifying or modifying anything in `column-view-browsing` (multi-column layout, in-column error states, keyboard navigation within a column view instance) — this change treats that capability as a black box that each navigation context instantiates.
- List-view or details-view navigation surfaces — out of scope until a future change; every navigation context in this change hosts a column-view-style instance only.
- The actual copy/move operations invoked when dragging between dual-pane panes — that behavior belongs to `file-operations` (sibling change); this change only ensures two independent, simultaneously-visible locations exist to make such operations convenient.
- Command palette, search-box integration inside the address bar, or search-scoped navigation — belongs to `instant-search`.
- Cloud sync, roaming, or multi-machine bookmark sync — bookmarks persist locally only, in this change.
- Session restore (reopening the exact tab/window layout from the previous run) — noted as an open question, not committed to in this change.

## Decisions

### D1: One shared `FastFilesEngine` connection; per-context state is purely "which path, which history"

Each tab, and each pane in dual-pane mode, is represented in-process by a lightweight `NavigationContext` struct: current path, the column-view instance's per-column selection/scroll state, and its own back/forward history stack. `NavigationContext` is **not** a connection object and does not own any IPC handle, pipe, IPC or `HANDLE` reference to the engine.

Instead, exactly one `EngineConnection` object per `FastFiles.exe` process (already established by the foundation change: one control-pipe subscription, one mapped-in-process view of the snapshot section, remapped only on generation-change notification) is shared by every `NavigationContext`. A `NavigationContext` asks the single `EngineConnection` for a directory listing at a given path; the connection either serves it directly from the already-mapped snapshot (the common case, zero IPC round trip) or, for paths not yet resident/fresh in the snapshot, issues the narrow refresh/priority-hint request the foundation's protocol already defines. The response is a plain read of shared, immutable memory — safe to hand to any number of concurrent readers without locking, because the snapshot is documented as read-only and double-buffered specifically so readers never observe a torn write.

**Why this is correct, not just convenient:** the snapshot is the entire filesystem view already, machine (session)-wide — it isn't scoped to "the folder currently open in some window." Two tabs looking at `C:\Users\me\Documents` and `D:\Projects` are two read cursors over the *same* shared dataset, not two different datasets. Duplicating the connection per tab would duplicate the memory-mapping/notification-subscription bookkeeping for zero benefit and would violate the foundation design's stated purpose of that snapshot (letting arbitrarily many in-process readers subscribe concurrently at zero per-read IPC cost). It would also complicate the degraded-mode and reconnect state machines (D5/D6 in the foundation design) by requiring them to be replicated and kept in sync N times instead of once.

**What is genuinely per-context, and why that's the right cut:** only "which path is this context currently looking at, what did it look at before, what was selected/scrolled in each open column" is per-tab/per-pane state — this is UI navigation state, not index state, and has no meaningful shared representation (two tabs are allowed to look at the same folder independently, each with its own selection). This mirrors how a web browser's tabs each keep their own history/scroll-position against one shared network stack/cache.

**Alternatives considered:**
- *Separate `EngineConnection` per tab/pane.* Rejected — multiplies control-pipe subscriptions and remapping bookkeeping with no functional benefit, and reintroduces exactly the kind of per-window connection lifecycle the foundation change's three-process split was designed to avoid needing (that split already pays for one connection per UI process; paying again per-tab buys nothing since the underlying data is identical).
- *Separate `FastFilesEngine` process per tab/pane.* Rejected outright — the engine is a per-logon-session singleton by design (foundation D2), not a per-window resource; this would also multiply memory for a snapshot that's supposed to be shared machine/session-wide.
- *A single global "current path" with tabs as saved/restored bookmarks of it (no true concurrency).* Rejected — this is not what "tabs" means to users (they expect simultaneously live, independently browsable views, matching every mainstream tabbed file manager e.g. the many third-party Explorer tab extensions, and browsers generally); it would also break dual-pane mode's entire purpose (two locations visible and usable at once).

### D2: Address bar — breadcrumb mode is default; click-to-edit switches to editable-text mode

The address bar has two mutually exclusive display modes for a given navigation context at a given moment:

- **Breadcrumb mode** (default): the current path rendered as a sequence of clickable segments (e.g. `This PC > C: > Users > me > Documents`), each segment navigating that same context to that ancestor path when clicked. This is the steady-state, low-friction mode most navigation happens in (mirrors Windows Explorer's own default).
- **Editable-text mode**: a plain text field containing the full current path as text, entered by (a) clicking in the empty space at the end of the breadcrumb trail, (b) clicking a dedicated small toggle affordance, or (c) a keyboard shortcut (e.g. Ctrl+L, matching the browser-address-bar convention). The user can select-all/retype/paste an entirely different path. Pressing Enter attempts navigation to the parsed path; Escape or focus-loss-without-Enter reverts to breadcrumb mode showing the *current* (unchanged) location, discarding the typed text — typing in the box never navigates anything until explicitly committed.

**Why both, not just one:** breadcrumb mode gives fast, mistake-proof "go up N levels" navigation (the dominant real-world action) with zero typing; editable-text mode is the only way to paste a full path (from a chat message, a script's output, a UNC share announcement, etc.) or type one directly, which breadcrumb-only UIs cannot do at all. This is exactly the toggle model Windows Explorer itself uses, chosen deliberately for user familiarity rather than inventing a novel interaction users would have to learn.

**Alternatives considered:**
- *Always-editable text field, no breadcrumb.* Rejected — loses one-click "go to parent folder" navigation and is slower/more error-prone for the common case of moving up or down a small number of levels.
- *Always breadcrumb, path entry via a separate modal dialog ("Go to folder…").* Rejected — adds a modal hop for a very common action (pasting a path); every mainstream competitor (Explorer, Finder's "Go to Folder" Cmd+Shift+G being the exception that proves the rule — even Finder has direct entry) supports inline direct entry.

**Path parsing and validation (applies to both typed and pasted input in editable-text mode):**
1. Trim leading/trailing whitespace; strip a wrapping pair of quote characters if present (common when pasting a path copied via Explorer's "Copy as path", which wraps in `"`).
2. Normalize trailing separators (one or more trailing `\` or `/` are accepted and stripped before lookup; an all-separators or empty string after trim is treated as invalid input, not as "root").
3. Accept absolute drive-letter paths (`C:\...`), UNC paths (`\\server\share\...`), and forward-slash variants by normalizing `/` to `\` before further processing (Windows accepts either, but internal state and display always use `\`).
4. Accept `%ENVIRONMENT_VARIABLE%`-style tokens (e.g. `%USERPROFILE%\Documents`) and expand them via `ExpandEnvironmentStrings` before resolution — a small, well-known convenience for power users pasting paths from scripts or documentation, not a general shell/glob syntax.
5. Reject relative paths (no drive letter or UNC prefix) explicitly rather than silently resolving them against some ambiguous "current directory" — a navigation context's only meaningful base is its own current path, and silently reinterpreting `..\foo` against it is more surprising than an explicit rejection with guidance text. (A bare `..` or `.\subfolder`-style relative segment *within* an otherwise-absolute path, e.g. `C:\Users\me\..\you`, is still resolved via standard path-canonicalization rules, since that's unambiguous once a root is known.)
6. After parsing to a well-formed absolute path or UNC path, existence/accessibility is checked (via the engine's snapshot if resident, else a direct unprivileged existence check) before committing navigation.

**Invalid/inaccessible-path feedback:** never a crash or an unhandled exception, and never a silently-ignored keystroke. Three distinct outcomes, each visibly different from the others:
- *Syntactically invalid* (unparseable, e.g. contains a reserved character `<>|?*` outside a recognized escape, or is relative) — the field is marked invalid (e.g. red outline) with inline text explaining why; focus stays in the field; nothing navigates.
- *Well-formed but does not exist / no longer exists* — same inline-invalid treatment, distinguishable text ("This location no longer exists").
- *Well-formed and exists but is not accessible* (permission denied) — navigation proceeds to that location, and the *destination* column-view instance shows its own in-column permission-denied state (already specified by `column-view-browsing`); the address bar itself does not block this case since existence, not permission, is what it can cheaply pre-check without racing the actual listing call.

This distinguishes "your input was bad" (address-bar-level feedback, nothing navigates) from "your input was fine but the destination has a problem" (navigation proceeds, the already-specified in-column error surface handles it) — reusing `column-view-browsing`'s existing permission-denied/vanished-directory states rather than inventing a second, competing error surface.

### D3: Back/forward history — folder-change events only, one independent stack per tab

A history entry is recorded when, and only when, a `NavigationContext`'s **current directory changes** — i.e., the root path the column-view instance is anchored on changes. This includes: clicking a folder to descend, clicking a breadcrumb segment, committing an editable-text-mode path, clicking a sidebar entry (known folder, bookmark, drive), and invoking Back/Forward itself (which moves the stack pointer without pushing a new entry). It explicitly excludes: selecting a different item within the already-displayed columns without descending, scrolling, resizing, or any change to a subordinate column's selection that does not move the context's primary location. This mirrors a web browser's history model (page navigations are recorded; scroll position within a page is not a distinct history entry) and matches user expectation of what Back "undoes."

Each `NavigationContext` (each tab; each pane, whether or not the pane itself later hosts multiple tabs — see D5) owns one independent, linear back/forward stack: navigating forward from history truncates any redundant forward entries past the current pointer exactly like a browser; there is no shared or merged history across tabs or panes. Opening a new tab starts that tab with an empty history and its own starting location (see D4) — it never reads from, appends to, or otherwise touches another tab's stack.

**Alternatives considered:**
- *Recording every selection change as a history entry.* Rejected — makes Back nearly useless (one click of Back would only move a highlighted selection, not the visible location), and doesn't match any mainstream file manager or browser's actual behavior.
- *One shared history across all tabs (a single global timeline).* Rejected — directly contradicts the "independent per-tab state" requirement and would make Back in one tab jump to a location the user never navigated in *that* tab, which is confusing and unrecoverable without per-tab bookkeeping anyway (so it saves nothing in implementation either).

### D4: Known-folder discovery vs. user bookmarks — separate sources, one sidebar section each

**Known folders** are discovered programmatically, not hand-maintained: enumerate the standard set (Desktop, Documents, Downloads, Pictures, Videos, Music, and similar `KNOWNFOLDERID`s already registered on the system) via `SHGetKnownFolderPath` (simple, per-ID calls, the common case) with `IKnownFolderManager` available as the enumeration path if a dynamic "walk everything registered" listing is later wanted rather than a fixed short list. This list is **not** user-editable content — it reflects the OS's own configuration (including any redirection, e.g. Documents relocated to a different drive or a business-managed profile), refreshed at startup and re-resolved if a `SHChangeNotify`-style known-folder-path-change notification fires. If a known folder's path no longer resolves (rare, e.g. a redirected folder on a currently-disconnected drive), it is shown but produces the same in-column vanished/inaccessible state as any other unreachable location on click, rather than being silently omitted (omitting it would be confusing — the user's own OS still lists it in real Explorer).

**Bookmarks/favorites** are explicit, user-initiated entries: "Add to bookmarks" (or drag-and-drop into the sidebar's bookmarks section) on any folder the user navigates to, with a user-assignable display name and reorderable position, removable individually. These are stored as a small local, per-user data file — a simple flat list (path, display name, sort order) — separate entirely from the filesystem index and from `establish-architecture-foundation`'s still-open "index storage shape" question, since this is a handful of user-entered rows, not indexed filesystem data. JSON in the user's local app-data folder is sufficient (see D6).

**Why these must stay two distinct sources rather than being merged into one editable list:** known folders need to always reflect what the OS actually reports (so they stay correct across profile redirection, business/managed-device policy, and future new default folders Windows adds) — hardcoding them as one-time-imported bookmarks would drift from reality the first time a known folder moves. Bookmarks need to be freely user-managed (add arbitrary folders, rename, reorder, remove) — treating them as OS-derived state would make ordinary user edits fight the OS's own source of truth. Keeping them as two clearly-labeled sidebar sections (see D5) lets each obey its own correct update/edit rules without a merge-conflict model.

**Alternatives considered:**
- *Hardcode known-folder paths (`%USERPROFILE%\Documents` etc.) instead of calling the Known Folder API.* Rejected — breaks under folder redirection (a documented, common enterprise and even personal scenario, e.g. moving Documents to a second drive), which `SHGetKnownFolderPath` handles correctly for free.
- *Let users freely edit/remove known folders, merging them into the bookmarks list.* Rejected per above — conflates OS-reported truth with user-authored state and complicates "restore defaults" semantics for no real benefit (a user who doesn't want to see Videos, say, is adequately served by the sidebar's collapsible-section model rather than needing deletion).

### D5: Sidebar — one collapsible panel, three internally-collapsible sections (Drives, Known Folders, Bookmarks)

The sidebar is a single vertical panel docked to one side of the navigation surface (leading/left edge, matching the OS-wide left-to-right reading convention and every mainstream Windows file manager), toggleable to fully collapsed (icon-only or fully hidden, showing only a re-expand affordance) to reclaim width for column view — this addresses the "without consuming excessive screen space" requirement directly, since column view already wants generous horizontal room.

Within the sidebar, three sections, each independently collapsible/expandable (remembering expand/collapse state across sessions) so a user who never uses Bookmarks can shrink that section to its header alone without losing the panel's Drives/Known-Folders sections:
1. **Drives** — enumerated volumes (from the engine, or directly via `GetLogicalDrives`/`GetVolumeInformation` if the engine hasn't surfaced volume data yet), each showing at minimum a label and used/free indication space permitting.
2. **Known Folders** — the `SHGetKnownFolderPath`-discovered set from D4, fixed order (OS-registered order or a small fixed sensible order), not reorderable by the user (see D4's rationale).
3. **Bookmarks** — the user-managed list from D4, user-reorderable, with inline add/rename/remove.

Clicking any entry in any section navigates the *currently active* navigation context (the focused tab, or the focused pane in dual-pane mode) to that path — it does not, by itself, open a new tab; opening in a new tab is a secondary action (e.g. middle-click or a context-menu item), consistent with how the same gesture already behaves for folders inside column view itself for consistency.

**Alternatives considered:**
- *Three separate docked panels instead of one sidebar with sections.* Rejected — multiplies chrome and screen-space cost, works against the explicit "doesn't consume excessive screen space" goal.
- *A single flat, unsectioned list mixing drives/known-folders/bookmarks.* Rejected — users can't tell OS-provided from self-added entries at a glance, and can't collapse just the section they don't use; sectioning costs little and directly serves the space-and-clarity goal.

### D6: Dual-pane mode — two panes, each a single navigation context (no per-pane tab strips) for this MVP

Dual-pane mode shows two `NavigationContext` instances side by side, each with its own address bar (in whichever mode it's currently in) and its own column-view instance, both fed by the one shared `EngineConnection` (D1). Exactly one pane is "active" (has focus) at a time for the purposes of sidebar-click routing (D5) and keyboard input; the inactive pane remains fully rendered and browsable by direct interaction (clicking into it makes it active), matching how dual-pane tools (Total Commander, most Explorer dual-pane extensions) behave.

For this MVP, **each pane is a single navigation context, not its own tab strip** — dual-pane gives exactly two simultaneous locations, not up to 2×N. Toggling dual-pane on takes the currently active tab's context and clones it as the starting point for the second pane (same path, fresh/empty history for the new pane, since it's a new context per D3); toggling off collapses back to one pane, keeping the previously-active pane's context and discarding the other (with no data loss risk, since navigation state, unlike file state, is disposable).

**Why not per-pane tab strips in this change:** the primary, explicitly stated purpose of dual-pane here is making cross-location copy/move convenient (per the proposal) — two visible locations already fully serves that. Per-pane tabs would multiply the state-and-UI surface (tab strip × 2, independent history × 2N, focus-routing rules for "which of up to 2N contexts is active") for a workflow this change isn't trying to solve yet, and every additional context is still cheap in engine-connection terms (D1) but not free in UI complexity, keyboard-focus rules, and testing surface. Keeping dual-pane and tabs as orthogonal-but-not-fully-crossed features (tabs exist at the top-level window; dual-pane splits the *currently active* tab's content area into two contexts) is a smaller, shippable MVP that still satisfies the proposal's stated goal, with per-pane tabs left as a clearly-scoped future extension (see Open Questions) rather than a foreclosed option — nothing in D1's shared-connection model prevents adding it later.

**Alternatives considered:**
- *Each pane hosts its own full tab strip (true 2×N grid).* Rejected for this change as scope creep relative to the proposal's stated motivation (cross-location copy/move); explicitly left as a viable future extension, not designed against.
- *Dual-pane replaces tabs entirely while active (only one pane, split differently).* Rejected — conflates two orthogonal concepts (how many top-level tabs exist vs. whether the active one is split into two panes) and would force users to choose between tabs and dual-pane rather than combining them.
- *Synchronized/mirrored navigation between panes (both panes always show the same path, or one path and its "opposite" side of a sync operation).* Rejected — the two panes are independent per the proposal ("two independent filesystem views"); forced synchronization is a distinct, heavier feature (directory-sync tooling) not asked for here.

### D7: Local persistence shape for bookmarks and closed-tab history

Bookmarks (D4) and a small ring buffer of recently-closed tabs (for the `tabs` capability's "reopen closed tab," e.g. last 10 closed, most-recent-first, consistent with the reopen-closed-tab convention in mainstream tabbed browsers) are persisted as one small local JSON file per user under the standard per-user local app-data path (e.g. `%LOCALAPPDATA%\FastFiles\workspace.json`), read at startup and written on change (debounced, not on every keystroke). This is intentionally decoupled from the filesystem index store entirely — it is tiny (kilobytes), user-authored, and has no relationship to MFT/USN data, so it does not need to wait on or be coupled to `establish-architecture-foundation`'s still-open index-storage-shape decision (SQLite vs. alternatives), which concerns index data of a completely different scale and update frequency.

**Alternatives considered:**
- *Store bookmarks in the same future SQLite index store.* Rejected — needlessly couples a tiny, independent piece of user state to a much heavier, still-undecided storage subsystem; also would make bookmarks unavailable if the index store were ever cleared/rebuilt for unrelated reasons (e.g. a corrupt-index recovery), which is an unacceptable trade for saving one small file format.
- *Windows Registry storage.* Rejected — a flat JSON file is simpler to back up, inspect, and hand-edit for recovery, with no meaningful advantage from the registry for this volume/shape of data.

## Risks / Trade-offs

- **[Risk] Sharing one `EngineConnection` across every tab/pane means a connection-level failure (e.g. the engine crashes or the privileged link drops) surfaces identically in every open tab at once**, rather than being isolated to one. → **Mitigation:** this is actually the *correct* shared behavior (there is only one real index/session regardless of window count), and `establish-architecture-foundation` already specifies the non-modal status-badge and degraded-mode fallback at the connection level (D5/D6 in that design) — every `NavigationContext` observes the same connection-state signal and each tab's column-view instance independently renders the already-specified in-column error/degraded state for its own current path; no new failure mode is introduced, it is simply visible in N places instead of one.
- **[Risk] Free-typed/pasted paths are a direct string-parsing attack surface for reserved characters, `..` traversal tricks, extremely long paths (`MAX_PATH` and beyond), and non-existent-drive-letter references** — get parsing wrong and the app could crash, hang, or navigate somewhere unintended. → **Mitigation:** D2's parsing pipeline is a fixed, ordered set of narrow steps (trim/dequote → separator normalize → slash normalize → env-var expand → canonicalize → existence check) with an explicit reject-and-explain outcome at every step rather than a best-effort guess; long-path (`\\?\`-prefixed) handling and non-existent-drive-letter cases both resolve to the same "well-formed but does not exist" feedback path, not a special-cased crash.
- **[Risk] Reusing `column-view-browsing`'s in-column error states for post-navigation permission/vanished-directory feedback (D2) creates an implicit dependency: if that capability's error-state rendering ever changes shape, this change's address-bar feedback story changes with it, unintentionally.** → **Mitigation:** documented explicitly here as an intentional reuse, not an accident; future changes to `column-view-browsing`'s error-state requirements should treat "the address bar relies on these being visually distinct and non-modal" as a compatibility constraint.
- **[Risk] "Reopen closed tab" and bookmarks both reference filesystem paths that can legitimately disappear or be renamed between when they were recorded and when the user acts on them** (a closed tab's folder gets deleted; a bookmarked folder gets moved). → **Mitigation:** both cases resolve through the same "well-formed but does not exist" address-bar/navigation feedback already designed in D2 — no separate error surface needed; stale bookmarks are left in the list (not silently auto-removed) since silent removal of user-authored data on a transient condition (e.g. a temporarily disconnected external drive) would be more surprising than an inert, clearly-erroring entry the user can remove manually.
- **[Risk] Debounced-write JSON persistence (D7) can lose the most recent few seconds of bookmark/tab-close changes on a hard crash or power loss between the triggering edit and the debounce flush.** → **Mitigation:** acceptable trade-off for this class of low-value, easily-redone data (re-bookmarking a folder takes seconds); flush-on-clean-shutdown covers the ordinary exit path, and the debounce window is kept short (low single-digit seconds) specifically to bound worst-case loss.
- **[Risk] Dual-pane's "no per-pane tabs" cut (D6) may feel limiting to power users who want, e.g., 4 simultaneous locations (2 panes × 2 tabs each) rather than 2.** → **Mitigation:** explicitly scoped as a future extension, not a foreclosed design; D1's shared-connection model already generalizes to any N contexts without rework, so adding per-pane tabs later is additive, not a redesign.

## Migration Plan

Greenfield addition — no existing tabs/bookmarks/history data exists yet to migrate (this is the first change to introduce any of it). First launch after this change ships starts with one tab, one pane, an empty bookmarks list, and the OS-discovered known-folders list populated immediately from `SHGetKnownFolderPath`. If `%LOCALAPPDATA%\FastFiles\workspace.json` (D7) is missing or fails to parse (corrupt file, future-version field it doesn't understand), the app starts from these same empty/default states rather than failing to launch — corrupt persisted workspace state is never a launch-blocking condition. No rollback concerns beyond "delete or ignore that one JSON file" if this change ever needed to be reverted.

## Open Questions

- **Session restore** (reopening the previous run's exact tab layout, per-tab paths, and dual-pane state on next launch) is not committed to in this change — D7's persisted file is scoped to bookmarks and closed-tab history only; whether to also persist and restore "live" open-tab layout is left for a follow-up decision once it's clear whether users want that (some prefer always starting fresh).
- **Per-pane tab strips in dual-pane mode** (D6's explicitly-deferred extension) — left open for a future change once real usage signals whether the 2-context MVP is actually limiting in practice.
- **Sidebar drive free/used space display** — whether to show a live-updating usage indicator per drive here, or defer that entirely to `storage-analysis`'s treemap work, is left unresolved; this change assumes at most a static label if any, deferring richer visualization to that sibling change.
- **Keyboard-shortcut inventory** (exact accelerators for new-tab/close-tab/next-tab/toggle-dual-pane/toggle-sidebar/focus-address-bar) is left to tasks.md/implementation rather than fixed here, since it doesn't affect the architecture, mirroring how `establish-architecture-foundation` left build-system choice to implementation.
