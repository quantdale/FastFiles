## 1. Method and measurement boundary

| evidence source | what it measures | boundary |
| --- | --- | --- |
| `GetProcessMemoryInfo(PROCESS_MEMORY_COUNTERS_EX)` | process private (commit) bytes, working-set bytes, peak values | the whole process, instrumented |
| `QueryWorkingSet` + `QueryWorkingSetEx` | resident pages split into shareable (mapped/section) vs private | page-granularity classification, not a sharing proof |
| replaced global `operator new`/`delete` (`tests/engine/bench_allocator_probe.h`) | live/cumulative requested and caller-usable bytes, live/total allocation counts, live peak | C++ allocations only; SQLite is compiled as C and allocates through `malloc`/`free`, so its plane appears in the private-bytes residual instead |
| `Projection::GetMemoryBreakdown()` | each projection category from live `capacity()`/`size()`/`bucket_count()`/element counts; `modeled_category_bytes` equals `Projection::EstimatedMemoryBytes()` exactly (asserted by `ffindexstore_projection_tests`) | the two `*ApproxNodeBytes` fields are element counts * `sizeof(...)` node-header approximations mirroring the estimator; stdlib node links, heap block headers, and rounding are not fabricated |

The instrumented executable replaces `operator new`/`delete` in **every** mode,
so its latency modes must not be used as uninstrumented latency evidence. The
probe's own 32-byte allocation header is excluded from the recorded requested
and caller-usable bytes; it appears in the process-private residual instead.

## 5. Repeat-rebuild, release, and harness-retention reconciliation

- The projection's own modeled categories are byte-identical from cycle 2
  onward at both scales (the only cycle-1 -> cycle-2 change is the free list's
  one-time capacity growth, a real modeled category). There is no per-cycle
  growth in any projection container.
- The small residual live-bytes movement between cycles is the benchmark's own
  report storage. Each retained `MemoryCapturePoint` is
  `harness_retention.capture_point_bytes` (656 bytes in both reports) plus,
  when the capture name is long enough for the heap, its name string; the JSON
  exposes that constant and per-capture allocator snapshots. The observed
  movement is **+3 live allocations at cycle 1 -> 2 and +1 per cycle
  afterwards**, with byte increments of 727 B then 656 + 32 B; the capture
  points dominate, but this is an observed bound, not the clean
  one-capture-per-cycle equality an earlier draft claimed. The remainder is a
  few hundred bytes per rebuild, independent of row count, and the projection's
  own categories are byte-identical from cycle 2 onward, which is the product
  claim this reconciliation supports.
- `after_pipeline_close` still holds the projection (the pipeline object is
  alive), and destruction (`after_pipeline_release`) returns to the process
  baseline: **still-owned allocations** fall to single-digit kilobytes while
  **allocator-retained pages** keep private bytes at a few MiB. The two are
  distinguishable in every capture.
- The repeated-rebuild path (rebuilding over an already-resident volume) is
  dominated by removal/index maintenance, not by the projection rebuild
  itself. That is pre-existing engine behavior, unchanged by this campaign,
  and is not a user-visible path (startup rebuild runs against an empty
  projection); it is recorded here because the cycle timings make it visible.
  The "unchanged" claim is artifact-backed: the archived comparison arms
  record 1M cycles 2-4 at 152.5/152.8/164.4 s (baseline) and 149.1/145.2/155.0 s
  (after the slack release), against 145.1/141.3/141.7 s for the final
  candidate; the spread is run-to-run variation on this host, and the
  corrections add no measurable rebuild cost.

## 6. Cross-layer duplication classification (updated from current source)

| layer | representation in the current tree | lifetime | classification |
| --- | --- | --- | --- |
| SQLite store | on-disk rows + name text (UTF-8), WAL | durable | intentional — the durable source of truth |
| projection rows | dense `ProjectionEntry` vector + free list | engine lifetime, evictable | intentional — the indexed query plane |
| interned names | one UTF-16 arena + offset/length table + hash-bucket index in `NamePool` | shared with rows | intentional — a name string exists once; no stored normalized copy exists (folds are computed on demand) |
| parent/child index | one flat open-addressing map with a contiguous child-index array | engine lifetime | intentional — no per-key heap vector |
| filename trigram index | posting vectors + non-ASCII entry list | engine lifetime, invalidated/rebuilt on mutation | intentional for speed — the suite proves eligible selective literal searches use it |
| LRU metadata | one dense `uint64` timestamp per entry slot | engine lifetime | intentional — drives bounded eviction; 8 bytes/slot |
| durable volume markers | `evictedVolumes_` set | engine lifetime | intentional — small, policy state |
| pooled export | per-directory name pools + entry arrays (`ExportDirectorySnapshotBoundedPooled`) | transient, one publication | transient — the retained production path; measured below |
| owning export | `std::map<wstring, SnapshotDirectory>` with per-entry `std::wstring` names | transient | reference path only — the measured comparison arm, not the production path |
| serialized generation | length-prefixed bytes in a named section | one current generation | transient/shared — the zero-IPC read plane; the engine keeps only the current mapping |
| UI/client parse | owning map built by `ParseSnapshot` in the client | per parsed generation | transient — client-owned; this probe measures the in-process parse, not the UI process |
| search results | per-query ids/row references | query-scoped | transient |

No accidental duplication was found in the name plane. The two owning copies
(view-layer export map and client parse map) are bounded by one publication
cycle each and are exactly the per-entry allocation sites the D5 isolation
matrix measured.

## 7. Retained corrections and the 8.3 decision

Two measured, locally executable memory corrections were retained:

1. **Bulk-rebuild capacity-slack release** (`Projection::ShrinkBulkRebuildCapacity`,
   `NamePool::ShrinkToFit`, `FlatChildrenMap::ShrinkToFit`). A bulk rebuild
   grows the name arena, offset table, flat child array, and posting vectors by
   geometric reallocation; the unused capacity is released once the load
   finishes, gated on a material-slack threshold so small single-volume
   reloads pay nothing. Content is unchanged (asserted), and the id->index flat
   table keeps its designed occupancy sizing.
2. **Dense per-slot LRU timestamps** (`lastAccessTimes_`): one `uint64` per
   dense slot instead of one `unordered_map<EntryKey, uint64_t>` node per
   entry. The key->slot map already exists, so the previous representation was
   a second hashed container. Removal, slot reuse, `CompactStorage`, and
   `CompactEntriesForIterationOrder` reset/remap the timestamps (the last one
   was an independent-review P1, fixed with a red-first regression test).

### 7.1 Comparison-arm provenance

The two pre-final rows above were measured during this finalization **before
the corrections were committed**, on a dirty tree at HEAD `2633529` with the
then-uncommitted decomposition seam, probe, and report mode. They are archived
next to this record as
`projection-memory/projection-memory-1m-comparison-baseline.json` (before
either correction) and
`projection-memory/projection-memory-1m-comparison-after-slack-release.json`
(after the slack release, before the dense LRU); both carry the earlier probe
convention in which `live_usable_bytes` included the probe header, so only
`live_requested_bytes`, `private_bytes`, and the cycle timings are compared
here. They are not reproducible from the current tree because the
pre-correction code never existed in a revision containing the report mode.
The artifact-backed, reproducible result is the final row: the two tracked
reports (`projection-memory-{200k,1m}.json`) produced by the tracked runner on
a clean tree.

The two corrections are below the campaign's 10% strong target taken alone

- the bulk-rebuild slack release alone removes 37,802,344 bytes (36.05 MiB,
  -8.2%) of still-owned live bytes and 22,204,416 bytes (21.18 MiB, -3.5%) of
  process private bytes;
- the dense LRU alone removes a further 56,776,362 bytes (54.15 MiB, -13.4%)
  of live bytes and 113,831,936 bytes (108.56 MiB, -18.7%) of private bytes,
  the larger private effect reflecting that a million small map nodes had also
  been holding heap pages;
- combined: -90,196,706 bytes (-86.02 MiB, -20.5%) live and -136,036,352 bytes
  (-129.73 MiB, -21.5%) private.

They are real reductions in **still-owned** bytes with no rebuild-time cost, no
content change, and no search, navigation, indexing, startup, or reconciliation
behavior change: they release capacity and replace a redundant hashed
container, and the focused plus full suites cover the eviction and rebuild
paths. `EstimatedMemoryBytes()` now models the dense LRU storage, so the memory
policy no longer over-counts LRU metadata.

Rejected or deferred with measured numbers (all shares use the 1M plateau
process private of 496357376 bytes = 473.36 MiB, the same denominator as the tables
above):

- **Identifier map (60,817,408 B = 58.00 MiB, 12.25%):** the flat
  open-addressing table holds 2,097,152 probes for 1,000,000 elements. The
  measured occupancy is 47.7%, but the smaller power-of-two (1,048,576) is
  95.4% occupied, above the 75% growth bound `EnsureInsertCapacity()` enforces,
  so the table would immediately grow and probe past `kMaxProbeDistance`. The
  2x sizing is a consequence of the probe-table invariant, not removable
  slack; reducing it requires redesigning the probe/load-factor contract.
- **Filename trigram accelerator (68,969,996 B = 65.77 MiB, 13.90%):**
  measured as the largest single removable structure, but the spec rejects
  trading search latency for bytes and the engine suite proves eligible
  selective literal searches use it. Retained.
- **Stdlib node links and the unmodeled remainder (24,490,157 B = 23.36 MiB):
  ** the whole live payload outside the modeled categories at 1M, covering the
  name hash index's node links and inner bucket vectors plus allocator
  bookkeeping. (An earlier draft cited 32 MB for node links; that figure was
  `name_hash_approx_node_bytes`, a *modeled* term already inside
  `modeled_category_bytes`.) Heap rounding is not a contributor: the probe
  records `live_rounding_overhead_bytes == 0` in every sample because every
  payload is 16-byte aligned and the probe header absorbs malloc's rounding.
- **Normalized-name and stored-path storage: 0 bytes by construction.** Folds
  are computed on demand and paths are reconstructed per call; there is
  nothing to remove.

is 0 in every snapshot (all payloads are 16-byte aligned), so rounding is not a
residual contributor.
